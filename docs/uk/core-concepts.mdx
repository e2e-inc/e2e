Тест складається з трьох видів кроків, і ви самі вирішуєте, яку частину
довірити агенту. Агент сам виконує дії для досягнення цілі та перевіряє стан
екрана за вашим описом, а локатор робить рівно те, що ви написали в коді.

| Крок | API | Викликає модель? |
| --- | --- | --- |
| [Ціль](#goals) | `agent.act` | Так, якщо крок не [закешовано](/cache) |
| [Перевірка](#assertions) | `agent.assert`, `agent.waitFor`, `agent.extract` | Так |
| [Локатор](#locators) | `screen` і `expect` | Ні |

Тест може бути повністю детермінованим: написаний лише на локаторах, він не
викликає модель і не потребує ключа API. Він також може бути повністю агентним
або поєднувати обидва підходи. Починайте з будь-якого й змінюйте по одному
кроку за потреби.

Детермінований тест без викликів моделі:

```ts title="tests/add-todo.e2e.ts"
import { test, expect } from 'e2e';

test('adds a todo', async ({ app, screen }) => {
  await app.open('/todos');
  await screen.getByLabel('New todo').fill('Buy milk');
  await screen.getByRole('button', 'Add').tap();

  await expect(screen.getByTestId('todo')).toHaveCount(1);
  await expect(screen.getByText('Buy milk')).toBeVisible();
});
```

Той самий застосунок із доданими діями агента:

```ts title="tests/todos.e2e.ts"
import { describe, test, expect } from 'e2e';

describe('todos', () => {
  test('the Done filter shows only completed todos', async ({ app, agent, screen }) => {
    await app.open('/todos');
    await agent.act('add todos "Buy milk" and "Walk the dog"');
    await agent.act('complete "Buy milk"');
    await agent.waitFor('"Buy milk" is completed and "Walk the dog" is open');

    await screen.getByRole('tab', 'Done').tap();

    await expect(screen.getByTestId('todo')).toHaveCount(1);
    await agent.assert('the only todo listed is "Buy milk"');
  });
});
```

Кожен тест перевіряє одну поведінку в три етапи: підготовка початкового стану,
виконання однієї цілі та перевірка результату. Завжди ставте `await` перед
кожним викликом `agent`, `screen` і `expect.poll`. Якщо тест завершиться, поки
крок ще триває, e2e позначить його як непройдений.

## Цілі

Метод `agent.act` отримує інструкцію природною мовою, виконує потрібні дії для
досягнення цілі та викидає помилку, якщо це не вдалося. Ви описуєте намір
користувача, скажімо застосування промокоду, а агент сам визначає потрібні
елементи керування:

```ts
await app.open('/checkout');
await agent.act('apply the discount code SUMMER');
```

Використовуйте ціль, коли зміни UI постійно змушують правити селектори або коли
сценарій має багато дій, але легко описується словами, наприклад заповнення й
надсилання форми. Перенесіть кнопку чи переробіть форму, і агент усе одно
виконає намір користувача, спираючись на те, що бачить на екрані. Цілі також
дають змогу моніторити staging або продакшн із реальними даними без підготовки
фіксованих тестових даних. Використовуйте тестовий акаунт, адже модель бачить
усе на екрані. Див. [Безпека](/security).

Щойно наступна перевірка в тесті проходить, e2e записує виконані дії та
[відтворює їх](/cache) під час наступного запуску без виклику моделі. Коли UI
змінюється і запис перестає відповідати застосунку, агент
[підхоплює сценарій і адаптується](/self-healing).

Починайте з одного виклику для поведінки, яку перевіряєте, і використовуйте
назви прямо з екрана. Коли наступному кроку потрібен відомий стан,
[розбийте сценарій](/agent-steps#split-a-long-flow-into-goals). Передавайте
тестові дані в `params`: [`Secret`](/authentication) приховує пароль від
моделі, а [`unique()`](/cache#what-must-match) дає кешу змогу відтворювати
значення, яке змінюється щоразу.

## Перевірки

Агентна перевірка оцінює поточний екран незалежно. Модель не бачить попередніх
кроків чи підсумків `agent.act`.

- **`agent.assert`** перевіряє екран у поточний момент і завершується помилкою,
  якщо твердження хибне або доказів недостатньо.
- **`agent.waitFor`** чекає, доки умова стане істинною.
- **`agent.extract`** зчитує структуровані дані з екрана за схемою, наприклад
  об'єктом Zod.

Використовуйте їх, коли вимогу задовольняють різні формулювання або варіанти
верстки, скажімо повідомлення про помилку валідації, яке пояснює проблему без
прив'язки до одного точного речення:

```ts
await agent.assert('the error message explains that an email address is required');
```

Оцінюйте зміст, а коли важливе дослівне формулювання, використовуйте
[локатор](#locators). Для графіка чи верстки передайте
[`vision: true`](/reference/agent#vision). Що бачить модель і які витрати має
кожен виклик агента, описано на сторінці [Як працює агент](/agent-steps).

## Локатори

Локатори звертаються до відомих елементів керування напряму, без виклику
моделі. Використовуйте `screen` і `expect`, коли точно знаєте потрібну дію або
очікуване значення:

```ts
await screen.getByLabel('Discount code').fill('SUMMER');
await screen.getByRole('button', 'Apply').tap();
await expect(screen.getByRole('status')).toHaveText('10% off');
```

Використовуйте локатори для механіки, яка сама є предметом тесту (порожнє
надсилання форми, комбінація клавіш або зміщення при перетягуванні), для
підготовчих тестів входу та в проєктах без моделі. Використовуйте `expect`,
коли результат є точним значенням, кількістю або станом, чи коли повідомлення
має містити конкретний текст.

Шукайте елементи спершу за роллю й назвою, далі за підписом і в останню чергу
за test ID, щоб тест звертався до елементів так, як їх розрізняє користувач.
Дія або перевірка одного елемента завершується помилкою, якщо локатор знаходить
кілька збігів, тому звужуйте вибір через `.filter()`, `.first()` або `.nth()`.
`expect` повторює перевірку до проходження або завершення тайм-ауту. Див.
[довідку з screen](/reference/screen),
[довідку з expect](/reference/expect#locator-matchers) та
[довідку з вебрушія](/reference/web) про перехоплення запитів, cookies, діалогові
вікна й завантаження файлів.

## Поєднання підходів

Обирайте підхід для дій і перевірок незалежно. Доручіть агенту пройти UI, що
змінюється, а потім перевірте точне значення за допомогою `expect`:

```ts
await agent.act('apply the discount code SUMMER');
await expect(screen.getByRole('status')).toHaveText('10% off');
```

Або заповніть і надішліть форму за допомогою локаторів, а потім перевірте через
`agent.assert`, чи пояснює повідомлення валідації суть проблеми.

- **Агент адаптується саме до вашого формулювання цілі.** Розмита інструкція може
  допустити небажаний результат. Якщо важливий конкретний шлях, назвіть його в
  цілі або виконайте ці дії локаторами. Перевірка `expect` після `agent.act`
  виявляє випадки, коли агент досяг цілі неправильним способом.
- **Виклики моделі додають затримку й витрати, а ще модель інколи помиляється.**
  [Кеш відтворення](/cache) здебільшого прибирає це для `agent.act`, тоді як
  агентні перевірки завжди виконуються наживо.

## Організація тестів

Групуйте тести за допомогою `describe` і задавайте `tags`, `retries` або
`timeout` для групи чи окремого тесту. Усі параметри наведено в
[довідці з test](/reference/test).

- **Починайте якомога ближче до потрібного екрана.** Кожен тест запускається в
  окремій спробі, тож створюйте дані у [фікстурі](/fixtures), відновлюйте
  [збережену сесію](/authentication), відкривайте прямий URL або використовуйте
  мобільний [deep link](/mobile#the-device-fixture).
- **Виносьте спільний код.** Використовуйте `const` для повторюваного локатора,
  хук або фікстуру для підготовки та [page object](/page-object-model) для
  екрана, з яким працює кілька тестів.
- **Об'єднуйте залежні тести** за допомогою [`{ serial: true }`](/reference/test#serial)
  на `describe`. Вони виконуватимуться по черзі на одному воркері й
  повторюватимуться разом.
