e2e працює в будь-якому CI-сервісі з Node 24.8+ (22.22.3+ на Node 22), а для
вебтестів також із [Bun](/reference/cli#bun) 1.4.3+. Типове завдання (job)
встановлює залежності, запускає застосунок або пристрій, виконує `e2e run` і
вивантажує `.e2e/`.

Для іншого CI-сервісу візьміть за основу workflow для
[GitHub Actions](/ci/github-actions). Як бронювати браузери чи пристрої в
хмарному сервісі, читайте на сторінці
[Хмарні браузери та пристрої](/integrations).

## Вивантаження звітів

Завжди вивантажуйте `.e2e/` наприкінці завдання, навіть коли тести падають:

| Шлях | Що всередині |
| --- | --- |
| `report.json` | Повний JSON-звіт про запуск |
| `junit.xml` | Звіт JUnit XML (із `--reporter list,junit`), зокрема відфільтровані тести як пропущені та збої запуску |
| `results/` | Трейси, знімки екрана, дампи екрана та відео (із `--video`) |

Спрямуйте інтеграцію тестових звітів вашого CI-сервісу на `.e2e/junit.xml`. У
GitLab файл `junit.xml` автоматично вбудовує посилання на знімки екрана збоїв.
Директорію `.e2e/` можна змінити параметром [`output`](/reference/config#output).

## Облікові дані моделі

Передайте ключ API, який очікує ваш провайдер, наприклад `AI_GATEWAY_API_KEY`
(див. [Моделі](/models)). Наборам тестів лише на локаторах ключ моделі не
потрібен.

<Warning>
Будь-яке завдання з ключем API відкриває його вашому тестовому коду, конфігу й залежностям. Надавайте секрети лише довіреним гілкам. Недовірений код із pull request запускайте без секретів і без токенів із правом запису. Див. [Безпека](/security).
</Warning>

Зберігайте ключі в секретах CI й налаштовуйте ліміти витрат там, де провайдер
це підтримує. GitHub Actions автоматично не передає секрети в pull request із
форків.

## Що змінюється в CI

Режим CI вмикається щоразу, коли змінна середовища `CI` має значення, відмінне
від порожнього рядка, `0` або `false`. Щоб перевірити поведінку CI локально,
виконайте `CI=1 npx e2e run`:

| Параметр | Локально | У CI |
| --- | --- | --- |
| `retries` | `0` | `1` |
| `workers` | половина ядер процесора | `1` |
| `cache`, якщо не задано | `read-write` | `read-only` |
| `.only` | дозволено | завершує запуск помилкою |
| `command.reuseExisting` | враховується | ігнорується |

Щоб змінити стандартну кількість воркерів і повторних спроб, передайте параметри:

<CodeGroup>
```bash npm
npx e2e run --workers 4 --retries 0
```

```bash pnpm
pnpm exec e2e run --workers 4 --retries 0
```

```bash bun
bunx e2e run --workers 4 --retries 0
```
</CodeGroup>

Щоб вимкнути надсилання [телеметрії](/telemetry#in-ci) з CI, додайте
`E2E_TELEMETRY_DISABLED: '1'` у блок `env` завдання.

## Мобільні завдання

Без [хмарного сервісу пристроїв](/mobile#hosted-devices) кожній платформі
потрібні окрема машина, збірка й пристрій:

| | iOS | Android |
| --- | --- | --- |
| Машина | macOS з Xcode і середовищем виконання симулятора | Linux із KVM (вкладеною віртуалізацією) |
| Збірка | Release-збірка `.app` для симулятора без підпису | Release-збірка `.apk` |
| Пристрій | Запущений симулятор | Запущений емулятор |

Готуйте release-збірку для обох платформ. Debug-збірка React Native або Expo
завантажує JavaScript із Metro, який ці завдання не запускають, тому застосунок
відкриється на екрані помилки. У прикладах використовується проєкт React Native
з директоріями `ios/` та `android/` у репозиторії. Якщо в проєкті Expo їх немає,
спершу виконайте `npx expo prebuild`.

Встановіть збірку, а потім запустіть набір тестів:

<CodeGroup>
```bash npm
# iOS
xcrun simctl install booted path/to/MyApp.app
npx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
npx e2e run --target android --reporter list,junit
```

```bash pnpm
# iOS
xcrun simctl install booted path/to/MyApp.app
pnpm exec e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
pnpm exec e2e run --target android --reporter list,junit
```

```bash bun
# iOS
xcrun simctl install booted path/to/MyApp.app
bunx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
bunx e2e run --target android --reporter list,junit
```
</CodeGroup>

Ці команди передбачають два таргети з назвами `ios` та `android`, кожен із
рушієм `mobile()` і заданим `bundleId` застосунку. Див.
[Підключення вашого застосунку](/mobile#point-at-your-app). Щоб набір тестів сам
встановлював збірку, задайте `app.appPath` і викличте `device.installApp()`.

Для будь-якого сервісу діють такі правила:

- **Окреме завдання для кожної платформи.** Запускайте `--target ios` на Mac, а
  `--target android` на Linux із KVM. Хмарні Mac працюють на Apple Silicon, де
  немає вкладеної віртуалізації, тож емулятор Android на них не запуститься.
- **Запускайте пристрій в окремому кроці.** Якщо жоден пристрій не запущено,
  рушій просить agent-device запустити його, але новий Linux-ранер не має образу
  емулятора. Окремий крок також дає змогу відрізнити збій запуску пристрою від
  збою тесту.
- **Фіксуйте середовище виконання iOS.** Симулятор, обраний за назвою
  (`iPhone 17`), запускає версію iOS за замовчуванням для цього образу, а дерево
  доступності змінюється між релізами iOS. Тоді оновлення образу ранера може
  зламати перевірку за локатором без жодних змін у вашому коді. У прикладах
  симулятор створюється на конкретному середовищі виконання й запускається за
  UDID. Замініть `iOS-26-5` на середовище, наявне в образі
  (`xcrun simctl list runtimes`).
- **Кешуйте `~/.agent-device/apple-runner/derived`.** Саме там agent-device
  збирає свій XCUITest-ранер під час першого керування симулятором. Не кешуйте
  всю директорію `~/.agent-device`: решта файлів містить стан останнього демона
  (daemon), і відновлена копія може зупинити наступний запуск із помилкою
  `Failed to communicate with daemon`.
- **Відтворюйте локальні записи.** Ключ кешу відтворення прив'язаний до
  застосунку, а не до пристрою, тож крок, записаний на вашому локальному
  симуляторі, відтвориться і на симуляторі в CI.
  [Закомітьте кеш відтворення](/cache#commit-the-replay-cache).

## Перевірка pull request перед злиттям

Будь-який ненульовий код виходу завершує завдання помилкою, включно зі збоєм
кроку агента. Зробіть завдання e2e обов'язковою перевіркою, щоб блокувати
злиття в разі збоїв, і не покладайтеся лише на підрахунок невдалих тестів у
файлі звіту, бо так легко пропустити помилки рівня запуску. Усі коди виходу
перелічено в [Налагодженні запуску](/debugging#read-the-failure).

Щоб перевірки pull request залишалися швидкими й передбачуваними:

- Задавайте в кожному `agent.act` кроки до однієї [цілі](/core-concepts#goals),
  а після цього додавайте перевірку за локатором або `agent.assert`.
- [Закомітьте кеш відтворення](/cache#commit-the-replay-cache), щоб записані
  кроки `agent.act` відтворювалися без викликів моделі. (Промахи кешу, передача
  керування агенту й агентні оцінки все одно звертаються до моделі.)
- Стежте за нестабільними тестами: e2e позначає як *flaky* кожен тест, який
  проходить лише під час повторної спроби.
- Використовуйте `--max-failures <n>`, щоб зупинитися раніше на зламаному
  розгортанні й не витрачати виклики моделі на решту тестів.
- Використовуйте `--max-duration <ms>`, щоб обмежити час виконання тестів
  (таймер запускається зі стартом тестів, без урахування запуску застосунку).

## Запуск лише тестів, яких стосується зміна

У pull request передайте `--changed-since`, щоб [фільтр тестів](/filters)
пропустив тести, на які зміни навряд чи вплинуть, і спершу запустив
найризикованіші файли. Без цього параметра (наприклад, у гілці `main`)
запускається весь набір тестів. Див.
[Додавання фільтра на основі моделі прийняття рішень](/filters#add-the-decision-filter).

## Кешування історії тривалості

Під час запуску з кількома воркерами `e2e run` використовує
`<output>/timings.json` (за замовчуванням `.e2e/timings.json`), щоб спершу
запускати найповільніші файли тестів. Зберігайте й відновлюйте цей файл у кеші
CI, щоб свіжі checkout зберігали прискорення. Приклад наведено на сторінці
[GitHub Actions](/ci/github-actions#cache-the-timings-history).

- Файл має суто рекомендаційний характер: відсутній або пошкоджений файл ніколи
  не впливає на результати тестів.
- Часткові запуски (`--grep`, `--last-failed`) не перезаписують тривалість
  файлів, які виконалися не повністю.
- Прив'язуйте ключ кешу до гілки з `main` як резервним ключем (і додайте індекс
  шарду, якщо використовуєте [шардинг](#sharding)).
- Пам'ятайте, що в CI за замовчуванням `workers: 1`. Щоб розпаралелити запуск,
  задайте `workers` або передайте `--workers`.

## Шардинг

Передайте `--shard <index/total>`, щоб розділити набір тестів між паралельними
завданнями CI. Кожна машина ділить набір детерміновано. Якщо шард може
залишитися без жодного тесту (скажімо, матриця ширша за набір), додайте
`--pass-with-no-tests`. Подробиці поділу див. у
[довідці з CLI](/reference/cli#flags).

У сервісі GitHub Actions матриця запускає окреме завдання для кожного шарду:

```yaml
jobs:
  e2e:
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3]
    steps:
      # ...
      - run: npx e2e run --shard ${{ matrix.shard }}/3 --pass-with-no-tests --output .e2e/shard-${{ matrix.shard }}
```

Щоб перезапустити невдалі тести шарду перед вивантаженням, виконайте
`e2e run --last-failed` із початковим `--output` цього шарду. Не передавайте
`--shard`, щоб повторний запуск використав уже відібрані збої цього шарду.

Щоб опублікувати єдиний звіт для всієї матриці, додайте фінальне завдання:

1. Вивантажте вихідну директорію кожного шарду з умовою `if: always()`. Додайте
   `report.json`, `report-with-reruns.json` (якщо є) і `results/`.
2. Задайте завданню об'єднання `needs: e2e` та `if: always()`. Перемкніться на
   ту саму ревізію, встановіть залежності проєкту й завантажте артефакти цього
   запуску workflow і спроби в окремі директорії, наприклад `.e2e/shard-1`,
   `.e2e/shard-2` і `.e2e/shard-3`.
3. Виконайте [`e2e merge-reports`](/reference/cli#e2e-merge-reports) для цих
   директорій. Мають бути присутні всі шарди, включно з порожніми. Вивантажте
   всю об'єднану директорію з `if: always()`, щоб посилання на трейси працювали.

<CodeGroup>
```bash npm
npx e2e merge-reports .e2e/shard-* --output .e2e/merged --reporter junit,markdown
```

```bash pnpm
pnpm exec e2e merge-reports .e2e/shard-* --output .e2e/merged --reporter junit,markdown
```

```bash bun
bunx e2e merge-reports .e2e/shard-* --output .e2e/merged --reporter junit,markdown
```
</CodeGroup>

Налаштовуйте публікацію звітів у PR, таку як `github()`, лише в завданні
об'єднання, наприклад передаючи туди окремий `--config`, і видайте цьому
завданню потрібні права. Якщо конфіг об'єднання лежить у піддиректорії,
передайте абсолютний шлях `--output`, щоб записати звіт поза нею. Щоб
перезапустити невдалі тести з усієї матриці, завантажте об'єднану директорію й
передайте команді запуску `--last-failed --output` зі шляхом до неї.

## Повторний запуск невдалих тестів

Параметр `--last-failed` запускає лише ті тести, які впали в попередньому
запуску (зчитуючи їх із `.e2e/report.json`). Його можна додати в той самий крок
CI:

```yaml
      - run: npx e2e run || npx e2e run --last-failed
```

Повторний запуск зберігає початкові артефакти, записує власні в `rerun-<n>/` і
створює об'єднаний файл `report-with-reruns.json` поруч із `report.json`. Якщо
ви запускаєте повторну спробу в окремому завданні CI, завантажте `report.json`
попереднього завдання (а також `report-with-reruns.json` і `results/`, якщо
потрібна повна історія).
