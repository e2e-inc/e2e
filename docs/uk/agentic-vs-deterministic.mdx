Агентне тестування дає змогу звичайними словами описати, що хоче зробити
користувач і що має показати екран. Агент сам обирає дії та перевіряє
результат, тому вам не доводиться постійно оновлювати селектори після змін у
UI.

У детермінованому тестуванні кожна взаємодія й перевірка прописані в коді.
Обидва підходи перевіряють результат для користувача, і в e2e їх можна вільно
поєднувати в одному тесті.

## Коли використовувати агентні тести?

Обирайте агентні тести, коли зміни UI постійно змушують вас правити селектори.
Вони також добре підходять для сценаріїв із багатьма діями, які легко описати
словами, зокрема заповнення й надсилання форми.

Метод `agent.act` описує намір користувача, скажімо застосування промокоду.
Агент сам визначає, які елементи керування використати і що зробити. Метод
`agent.assert` перевіряє, чи показує екран потрібний результат, на кшталт
знижки в підсумковій сумі.

Ось приклад тесту з фікстурами `app` та `agent`:

```ts
await app.open('/checkout');
await agent.act('apply the discount code SUMMER');
await agent.assert('the checkout shows code SUMMER applied with a 10% discount');
```

Вам не потрібно називати поле для промокоду, кнопку його застосування чи
елемент, що показує результат.

Тести, прив'язані до CSS-класів або test ID, доводиться правити щоразу, коли ці
ідентифікатори змінюються. Перенесіть кнопку або переробіть форму, і агент усе
одно виконає намір користувача, спираючись на те, що бачить на екрані.

Агентні тести дають змогу моніторити застосунок із реальними даними на staging
або в продакшні без підготовки фіксованих тестових даних, адже агент адаптується
до вашого застосунку. Використовуйте тестовий акаунт: модель бачить усе, що є
на екрані. Див. [Безпека](/security).

Для складного сценарію опишіть кроки до одного результату природною мовою. Про
те, коли розбивати сценарій на кілька викликів і чекати на проміжний стан,
читайте в розділі [Цілі](/core-concepts#goals).

## Коли використовувати агентні перевірки?

Агентні перевірки стають у пригоді, коли вимогу задовольняють різні
формулювання або варіанти верстки. Наприклад, повідомлення про помилку валідації
може пояснювати проблему без прив'язки до єдиного точного речення:

```ts
await agent.assert('the error message explains that an email address is required');
```

Для візуальної перевірки додайте `vision: true`, щоб модель також отримала
знімок екрана:

```ts
await agent.assert('the chart trends upward', { vision: true });
```

Метод `agent.assert` перевіряє поточний екран і завершується помилкою, якщо
твердження хибне або доказів недостатньо. Використовуйте `agent.waitFor`, коли
інтерфейсу потрібен час, щоб дійти до очікуваного стану. Обидва методи описано
в розділі [Перевірки](/core-concepts#assertions).

## Коли використовувати детерміновані тести?

Використовуйте локатори для низькорівневої механіки, яка сама є предметом тесту
(порожнє надсилання форми, комбінація клавіш або зміщення при перетягуванні),
для підготовчих тестів входу чи в проєктах без моделі. Ви задаєте кожне поле й
кнопку в коді, як у цьому тесті промокоду:

```ts
await app.open('/checkout');
await screen.getByLabel('Discount code').fill('SUMMER');
await screen.getByRole('button', 'Apply').tap();
await expect(screen.getByRole('status')).toHaveText('10% off');
```

Такі дії та перевірки не викликають модель. Надавайте перевагу ролям і
підписам, щоб тест звертався до елементів так, як їх розрізняє користувач.
Детерміновані тести не зобов'язані залежати від CSS-класів або test ID.

Використовуйте детерміновані перевірки, коли очікуваний результат можна задати
як точне значення, кількість або стан. Перевірка відбувається напряму, без
участі моделі. Якщо повідомлення валідації має містити точне формулювання,
перевірте цей текст за допомогою `expect`.

## Поєднання агентних і детермінованих тестів

Обирайте підхід для дій і перевірок незалежно. Ви можете доручити агенту пройти
UI, що змінюється, а потім перевірити точне значення за допомогою `expect`:

```ts
await agent.act('apply the discount code SUMMER');
await expect(screen.getByRole('status')).toHaveText('10% off');
```

Можна й навпаки: заповнити та надіслати форму за допомогою локаторів, а потім
перевірити за допомогою `agent.assert`, чи пояснює повідомлення валідації суть
помилки.

Адаптація спирається на ціль, яку ви написали. Розмита інструкція може
допустити небажаний результат. Якщо важливий конкретний шлях, прямо назвіть його
в цілі або виконайте ці дії за допомогою локаторів. Перевірка `expect` після
`agent.act` виявляє випадки, коли агент досяг цілі неправильним способом.

Виклики моделі додають затримку, збільшують витрати й інколи призводять до
помилок. [Кеш відтворення](/cache) здебільшого вирішує це, відтворюючи записані
дії `agent.act` без жодного виклику моделі, тоді як перевірки завжди
виконуються наживо. Коли UI змінюється і запис перестає відповідати
застосунку, агент підхоплює сценарій і адаптується, якщо не увімкнено суворий
режим кешу. Див. [Самовідновлювані тести](/self-healing).
