---
title: Electron
description: Test an Electron app through Chromium's accessibility tree, window by window.
---

`@e2e-dev/electron` runs tests on Electron apps. It launches the app, reads
each window through Chromium's accessibility tree over the DevTools protocol,
and drives it with trusted input. Tests use the same `agent`, `screen`, and
`expect` APIs as browser tests.

<Note>
  The Electron engine is new. It is tested on macOS and Linux, and not yet on
  Windows.
</Note>

## Set up

Install the runner, the engine, and Electron:

<CodeGroup>
```bash npm
npm install --save-dev e2e @e2e-dev/electron electron
```

```bash pnpm
pnpm add --save-dev e2e @e2e-dev/electron electron
```

```bash bun
bun add --dev e2e @e2e-dev/electron electron
```
</CodeGroup>

The engine starts the `electron` package installed in the project. Electron 45
and later download their binary on first use; the engine does this one time
per run, before the first test. To check the setup, run `npx e2e doctor`.

A packaged app on an older Electron works too, back to Electron 22. Before
Electron 25, a screenshot is withheld while the app shows a modal `<dialog>`
or a fullscreen element, which would paint over the masks.

## Point at your app

Set the target's `app.appPath` to the app's directory or main script, relative
to the project root. `app.launchArguments` go after it on every launch, where
the app reads them in `process.argv`. The engine's own `--inspect=0`,
`--remote-debugging-pipe`, `--force-color-profile=srgb`, and
`--user-data-dir=<directory>` are there too, and `--no-sandbox` on Linux, so
an app that parses its arguments strictly must allow them. Screenshots are in
sRGB on every display; pass your own `--force-color-profile` in `args` to
change that.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { electron } from '@e2e-dev/electron';

export default {
  targets: [
    {
      name: 'electron',
      engine: electron(),
      app: { appPath: '.', launchArguments: ['--no-update-check'] },
    },
  ],
  credentials: {
    ada: { username: 'ada', password: process.env.ADA_PASSWORD ?? '' },
  },
} satisfies E2EConfig;
```

To test a packaged app, set `electron({ executablePath })` to its binary, such as
`'dist/mac/MyApp.app/Contents/MacOS/MyApp'` (not the `.app` directory),
and leave out `appPath`. The example's `ADA_PASSWORD` must be set, to at
least 6 characters, for the config to load.

## Write a test

Import `test` from `@e2e-dev/electron`. `app.open()` launches the app and
waits for a window to load its page; with a splash screen still loading, that
is the app's next window. Every test starts on an empty user-data
directory and ends with the app quit. `app.restart()` launches it again on
the same data, and `app.clearState()` on empty data. `app.open()` while the
app runs relaunches it on the same data, as `app.restart()` does.

```ts title="tests/sign-in.e2e.ts"
import { test } from '@e2e-dev/electron';
import { credentials, expect } from 'e2e';

test('signs in and opens settings', async ({ app, screen, electron }) => {
  const ada = credentials.user('ada');
  await app.open();
  await screen.getByRole('textbox', 'Username').fill(ada.username);
  await screen.getByRole('textbox', 'Password').fill(ada.password);
  await screen.getByRole('button', 'Sign in').tap();
  await expect(screen.getByTestId('status')).toContainText('Signed in as ada');

  await screen.getByRole('button', 'Open settings').tap();
  await electron.useWindow({ title: 'Settings' });
  await expect(screen.getByRole('heading', 'Settings')).toBeVisible();

  const userData = await electron.evaluate(({ app: main }) => main.getPath('userData'));
  expect(userData).toContain('e2e-electron-');
});
```

Roles and names are the ones Chromium computes, so `getByRole`, `getByLabel`,
`getByText`, `getByPlaceholder`, and `getByTestId` work as on the web, apart
from the differences in the table below.
`getByLabel` matches a field's accessible name: a field whose `aria-label`
overrides its `<label>` is found by the `aria-label` only.
`getByTestId` reads `data-testid`; set another attribute with
`electron({ testIdAttribute })`.

The `electron` fixture has these methods:

| Method | What it does |
| --- | --- |
| `evaluate(fn, arg?)` | Runs `fn` in the main process with the `electron` module, typed by your project's `electron` package, and returns its serializable result. `fn` is sent as text, so pass values as `arg`. A secret is refused as `arg` |
| `windows()` | Lists the open windows, in the order they opened: each one's `index`, `title` (the document's), `windowTitle` (the OS window's, when it differs), `url`, and `shown`, true for the window `screen` reads |
| `useWindow(which, { timeout }?)` | Makes `screen` read a window: an index, or `{ title, url }`. A string matches the whole title or URL; use a RegExp for part of one. `title` matches the document's title or the OS window's. It waits for the window to open, up to `timeout` or the action timeout |
| `locator(selector)` | A locator for a CSS selector in the window's document |

`evaluate` returns what survives serialization: a `BrowserWindow` comes back
as a plain object, and a function or a `Map` as `undefined` or `{}`. Return
plain data, and pass `arg` as JSON. `require` is not in scope inside `fn`; use the `electron` module
it receives, or `process.getBuiltinModule('node:fs')`.

## What differs from the web

| Area | On an Electron target |
| --- | --- |
| Windows | `screen` reads one window: the one `useWindow()` picked, else the first. When that window closes, it reads the window shown before it, else the newest still open. A window the app opens does not take over. The agent sees the windows as tabs and switches between them. A DevTools window is not listed, and neither is a window or view that has loaded no page yet; each `WebContentsView` is a window of its own. A `<webview>` guest is listed as a window too. The order of several views in one window can change between launches; pick them by title or URL. A window whose renderer crashed fails reads with `APP_NOT_OPEN` after waiting up to 2 seconds for a reload; reload it with `electron.evaluate(({ BrowserWindow }) => BrowserWindow.getAllWindows()[0].webContents.reload())` |
| Text queries | `getByText` matches an element's text, as on the web, but not a `<textarea>`'s content. `getByLabel` matches any element's accessible name, such as a heading or a button with the same words, a fieldset by its legend, or an image by its alt text; narrow it with `getByRole('textbox', name)`. Each run of text is a match of its own, so `getByText('Line one Line two')` finds text split by a `<br>`. |
| Role states | `getByRole(role, { expanded: false })`, and `checked`, `selected`, or `pressed` set to `false`, also match elements that have no such state |
| Dialogs | An `alert()` or `confirm()` nothing answers is dismissed, so `confirm()` returns `false`, and the test's next step fails with `unhandled confirm dialog`, as on the web without a handler. Set `electron({ dialogs: 'accept' })` or `'dismiss'` to answer every dialog; each one is then a line in the attempt's log. Electron does not support `prompt()`: it throws in the page. A `beforeunload` guard does not stop the engine from quitting the app |
| Keyboard | Keys reach the page over the DevTools protocol. Menu accelerators and the main process's `before-input-event` don't see them; reach a menu item with `electron.evaluate`. There is no `keyboard` fixture to hold a key down. A key pressed on an element that takes no focus goes to the element that has it |
| Clipboard | The app uses the OS clipboard: a test's copy overwrites yours, a paste reads it, and tests in parallel workers share it. Run clipboard tests with `workers: 1` |
| Input | Input reaches one page's content directly, past the OS: a button in a `-webkit-app-region: drag` area, or under a view laid over the window, takes a tap a user's click would not reach |
| Theme | `prefers-color-scheme` follows the app's `nativeTheme` and the OS, as when a user runs it |
| Locale | The app runs in the OS locale, so text Chromium supplies, such as an `<input type="submit">` with no value, follows it. Pass `args: ['--lang=en-US']` for the web's English |
| Long press | Holds for 800 ms by default, where the web holds for 500 ms |
| Packaged apps | A packaged app built with the `EnableNodeCliInspectArguments` fuse off opens no inspector in its main process. `screen`, `expect`, and the agent work on it, but `electron.evaluate` fails, `windows()` reports no `windowTitle`, and `useWindow({ title })` matches the document's title only. On macOS, an unsigned build that reads the keychain (`safeStorage`) waits on a prompt and opens no window: pass `electron({ args: ['--use-mock-keychain'] })` |
| Headed | Electron has no headless mode. Windows show unless the app hides them, and `--headed` changes nothing. On Linux CI, run under a virtual display such as `xvfb-run` |
| Reading | The agent's screen and role queries leave out content under `aria-hidden` or `inert`; text and test-id queries still find it, and an action on an inert element fails. Content that is not rendered (`display: none`, `hidden`, a closed `<details>`) is left out, where the web reads it as hidden: a test id or `electron.locator()` still finds such an element. An element with no size reads as hidden, and role queries skip it, so an empty `role="alert"`, or an option of a closed `<select>`, is not found by role; `electron.locator('select option')` finds the options. Text reads as rendered, `text-transform` applied, so `getByText` matches the rendered case (the text of a label for a checkbox or radio reads as written), and the children of a flex or grid container read with no space between them. An element's box is its whole box, though a scroll container shows only part of it. A `<summary>` reads as a button, and open shadow content is in document order. Nested documents (`iframe`, `webview`) are not read: the frame is a node with nothing under it |
| Selectors | `electron.locator()` matches in the window's document and in each open shadow root, one root at a time: a selector does not cross a shadow boundary. It never enters a frame |
| Uploads | `setInputFiles` takes file paths, on a file input or on a button whose click opens a file chooser. In-memory files are not supported |
| Downloads | A file the app downloads is saved in a `Downloads` directory inside the attempt's user-data directory, and deleted with it, unless the app's own `will-download` handler sets a path. In an app that opens no inspector, this covers the default session only, not a `partition`. A test can read it at `electron.evaluate(({ app: main }) => main.getPath('downloads'))`, but cannot wait for one |
| Not supported | Video recording, `browser`-only APIs (routes, downloads, cookies), `app.back()`, session save and restore, `toBeInViewport`, and a project tool's [computed-style reads](/tools#read-a-nodes-computed-style). A test cannot read the app's console |
| Workers | No limit. A single-instance lock is per user-data directory, so it does not stop parallel tests. An app that sets its own data directory with `app.setPath('userData', …)` keeps its data across tests, `app.clearState()` does not empty it, and its lock fails on a second worker: set `workers: 1` |
| Secrets | A password field shows no value, and reading it (`inputValue`, `toHaveValue`) fails with `POLICY_DENIED`. Screenshots paint every password field and nested document (`iframe`, `webview`, `embed`, `object`) black. A password field or nested document inside a closed shadow root is out of every mask's reach: the agent gets no screenshot, and `app.screenshot()` fails with `POLICY_DENIED`, as it does when such an element appears or moves while a screenshot is taken. A mask is a box drawn over the element before the capture, with animations stopped: what the app paints outside that box, such as a CSS reflection, or styles that hide the masks, show in the image. A text input drawn as a password field with `-webkit-text-security` is not a password field, and its value is read |
| Debugging port | The engine drives the app's windows over a pipe that no other process can reach. The main process listens on a loopback inspector port for the whole test, with no authentication: any process on the machine can connect to it while a test runs |

<Warning>
  An Electron app loads its own pages, often `file:` ones, and a link or a
  script in one can take a window to any file the user can read. While a
  window shows a local file outside the app's own directory, the agent gets
  no observation of it, the trace and failure evidence keep no screen of it,
  and `app.screenshot()` and `screen.tree()` fail with `POLICY_DENIED`. A
  test's own locators still read it. The app's directory is what its main
  process reports as `app.getAppPath()`.
</Warning>

## Options

| Option | Type | Default | What it sets |
| --- | --- | --- | --- |
| `executablePath` | `string` | the project's `electron` | The binary to start, such as a packaged app's |
| `args` | `string[]` | `[]` | Electron and Chromium switches, passed before the app path. Not `--user-data-dir`, `--inspect`, `--inspect-brk`, `--remote-debugging-port`, or `--remote-debugging-pipe`, which the engine sets; `app.launchArguments` cannot set them either |
| `env` | `Record<string, string>` | `{}` | Variables added to the app's environment. The app does not get the run's environment, which holds provider keys and tokens: only what a process needs to start and draw (`PATH`, `HOME`, the locale, the temp directory, the display, and the Windows system variables). Pass anything else the app reads here. Not `ELECTRON_RUN_AS_NODE` or `NODE_OPTIONS` |
| `launchTimeout` | `number` | `30000` | How long `app.open()` waits for a window to load, in milliseconds. The config's own `launchTimeout` bounds something else: the engine's start |
| `testIdAttribute` | `string` | `'data-testid'` | The attribute `getByTestId` reads |
| `settle` | `number \| false` | `100` | How long the engine waits after an agent action before the agent reads the screen |
| `dialogs` | `'accept' \| 'dismiss'` | unset | How every `alert()` and `confirm()` the app opens is answered. Unset, one is dismissed and fails the test's next step |
