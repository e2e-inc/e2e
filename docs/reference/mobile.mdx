`@e2e-dev/mobile` is the engine for iOS simulators, Android emulators, and
connected phones, driven through
[agent-device](https://github.com/callstack/agent-device). It contributes the
`device` fixture. `agent`, `app`, `screen`, and `expect` work as they do
everywhere; this page covers what is specific to a device target.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

export default {
  targets: [
    { name: 'iphone', engine: mobile({ platform: 'ios' }), app: { bundleId: 'com.apple.Preferences' } },
  ],
} satisfies E2EConfig;
```

```ts title="tests/settings.e2e.ts"
import { expect } from 'e2e';
import { test } from '@e2e-dev/mobile';

test('General opens in dark mode', async ({ app, device, screen }) => {
  await device.setAppearance('dark');
  await app.open();
  await screen.getByText('General').tap();
  await expect(screen.getByText('About')).toBeVisible();
});
```

- Import `test` from `@e2e-dev/mobile` to have `device` typed. Declare
  `platforms: ['ios', 'android']` in a suite that also runs on the web.
- Choose **Mobile (iOS/Android)** in `e2e init` to add the package with a
  Settings example. iOS needs Xcode and a simulator; Android needs the Android
  SDK and an emulator.
- The package includes a compatible version of `agent-device`; no separate
  installation is needed.

## Reference

### Engine

`mobile(options)` creates an engine for one platform. Create one for each
platform you test, and use `platforms: ['ios']` or `platforms: ['android']`
on tests with platform-specific labels or operations.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';
import { mobileTools } from '@e2e-dev/mobile/tools';
import { gateway } from 'ai';

const iphone = mobile({ platform: 'ios' });
const pixel = mobile({ platform: 'android' });

export default {
  targets: [
    { name: 'iphone', engine: iphone, app: { bundleId: 'Settings' } },
    { name: 'pixel', engine: pixel, app: { bundleId: 'com.android.settings' } },
  ],
  workers: 1,
  agents: {
    default: {
      model: gateway('openai/gpt-6-luna-fast'),
      tools: mobileTools(iphone, pixel),
    },
  },
} satisfies E2EConfig;
```

`mobile()` takes `MobileOptions`: which devices the engine drives and how.
The app under test is the target's `app`, not an engine option; see
[The app under test](#the-app-under-test).

| Option | Type | Default |
| --- | --- | --- |
| [`platform`](#platform) | `'ios' \| 'android'` | required |
| [`device`](#device-option) | `string \| readonly string[] \| DeviceProvider` | every booted device |
| [`session`](#session) | `string` | `e2e-<target name>` |
| [`snapshot`](#snapshot) | `'full' \| 'interactive'` | `'full'` |
| [`settle`](#settle) | `number \| false` | `150` |
| [`transition`](#transition) | `number` | `500` |
| [`videoTouches`](#videotouches) | `boolean` | `true` |

Every optional value also accepts `undefined`, so values read straight from
`process.env` need no conditional spread.

| Throws | When |
| --- | --- |
| `INVALID_CONFIG` | An empty `device` list, a blank `device` name, or a blank or non-string list entry. |
| `INVALID_CONFIG` | A `device` value that is neither a string, a list, nor a valid provider: a provider without a non-empty `name`, without `acquire()` or `release()`, or with a `record` that is not a function. |
| `INVALID_CONFIG` | `platform` is missing or not `'ios'` or `'android'`; the match is case-sensitive. |
| `INVALID_CONFIG` | A provided `snapshot` value is not `'full'` or `'interactive'`, or a provided `videoTouches` value is not a boolean. |
| `INVALID_CONFIG` | An option `mobile()` does not take, such as `mobile({ app })` and the other old app options. The message names the nearest known option for a likely typo, or lists every option. |
| `INVALID_CONFIG` | `settle` or `transition` is not a non-negative integer of milliseconds (`settle` may also be `false`). |

#### `platform`

```ts
readonly platform: MobilePlatform;
```

```ts
mobile({ platform: 'android' });
```

#### `device` option

```ts
readonly device?: string | readonly string[] | DeviceProvider | undefined;
```

```ts
mobile({ platform: 'ios' }); // default: every booted iOS device no other agent-device session holds
mobile({ platform: 'ios', device: 'iPhone 17' });
mobile({ platform: 'android', device: 'emulator-5554' });
mobile({ platform: 'ios', device: ['iPhone 17', 'iPhone 17 Pro'] });
```

- A name picks a simulator or emulator by name, simulator UDID, or emulator
  serial (`emulator-5554`), or a connected phone by name.
- A list is a pool: the engine declares one worker per entry and worker slot
  `n` drives the `n`th, so `workers` at or above the pool size runs the
  target's files across every device at once.
- Without `device`, the pool is every booted device of the platform at
  [`prepare`](#boot-and-prepare) that no other agent-device session holds, as
  many as the run has slots. A paired iPhone or iPad that is reachable (USB or
  network) counts as booted. With every booted one held, `prepare` fails.
- With none booted, agent-device boots a shut-down one: on iOS an iPhone over
  an iPad over an Apple TV, on Android a phone or tablet over a TV, then the
  newest OS, then name order. A stopped Android emulator reports no OS
  version, so the name decides.
- A `DeviceProvider` leases hosted devices instead, one per worker slot at
  `prepare`, and holds each lease until the run ends.
- `device.closeApp()` ends the agent-device session, so another session can
  take the device.
- Two workers never drive the same device, as long as each `device` entry
  names a different one.
- Without `device`, a booted device nothing holds, such as one you are using
  by hand, is in the pool: name the device to keep the run off it.
- A pooled device that another agent-device session claims while the run
  prepares is swapped for the next free one. With none free, a run with
  several workers goes on with one worker fewer. A named device or a
  provider's lease is never swapped.
- [Hosted devices](/mobile#hosted-devices) has the `DeviceProvider` contract
  and an example provider.

#### `session`

```ts
readonly session?: string | undefined;
```

```ts
mobile({ platform: 'ios', session: 'checkout' }); // default: e2e-<target name>
```

- The name comes before the worker slot: slot `n` drives its device under
  `<session>-<n>`, `e2e-<target name>-<n>` by default.
- One run per session at a time: concurrent runs on the same session
  interleave taps.
- Without this option, a `launch()` host drives
  `e2e-<target name>-<host token>-<n>`, a session of its own.

#### `snapshot`

```ts
readonly snapshot?: 'full' | 'interactive' | undefined;
```

```ts
mobile({ platform: 'android', snapshot: 'interactive' }); // default: 'full'
```

What an observation captures. `'full'` includes static text, so judgments
can read values. `'interactive'` keeps only actionable nodes and is cheaper
on screens with long lists.

#### `settle`

```ts
readonly settle?: number | false | undefined;
```

```ts
mobile({ platform: 'ios', settle: 300 }); // default: 150
```

- How long the UI must hold still, in milliseconds, after a tap, fill, screen
  scroll, or back before the agent observes again. `false` skips the wait.
- Raise it for slow devices or apps that settle in stages, or lower it to `0`
  to keep only the first re-observation.
- A test's steps do not settle, except `device.back()`: `expect` verifies
  their outcome, and [`transition`](#transition) covers a control that is
  still arriving.

#### `transition`

```ts
readonly transition?: number | undefined;
```

```ts
mobile({ platform: 'ios', transition: 800 }); // default: 500
```

The wait, in milliseconds, before acting on a control that just appeared or
moved. Raise it for slower transitions.

- An unmoved control is acted on at once only when keyboard visibility is
  unchanged. Opening or closing the keyboard also uses the remaining budget.
- A screen swipe in a test waits out the remaining budget before scrolling.

If the control changes during the wait, the action finds it again within its timeout before acting.

`back`, `home`, `pressRemote`, `pressButton`, `shake`, `lock`, `unlock`, `alert`,
`dismissKeyboard`, `setOrientation`, and `fold` on [`device`](#device) change the screen, so they count as actions for this
budget the way a tap does. A control that arrives with the screen they reveal
waits out the budget before the next action lands on it.

`fill` and `clear` on a field that is missing, changed its security state, or
was captured incompletely return `NODE_STALE` before typing, then retry after
a fresh observation. Non-input targets return `UNSUPPORTED_CAPABILITY`. An
iOS `other`, the type of an element the platform did not classify, is typed
into when it holds a value or only text, as a custom-drawn field (Compose
Multiplatform, Flutter) can.

#### `videoTouches`

```ts
readonly videoTouches?: boolean | undefined;
```

```ts
mobile({ platform: 'ios', videoTouches: false }); // default: true
```

Whether a video recording draws agent-device's touch indicator where a test
tapped. `false` records the plain screen and skips the pass that draws the
indicator once the recording stops. On a hosted daemon such as Expo
Simulators' that pass can outlast the attempt's `cleanupTimeout`.

#### The app under test

The app is the target's `app`: `bundleId`, `appPath`, `launchArguments`,
`permissions`, `identity`, and `environment` are documented under
[the app under test](/reference/config#the-app-under-test).

```ts title="e2e.config.ts"
export default {
  targets: [{ name: 'ios', engine: mobile({ platform: 'ios' }), app: { appPath: './build/MyApp.app' } }],
} satisfies E2EConfig;
```

- A device target needs `app.bundleId` or `app.appPath`.
- `app.open()` launches the target's app fresh. An attempt launches nothing
  on its own, so a test starts where the previous one left the app.
- `app.open(path)` opens the path as a link in the app when the target
  declares [`app.linkBase`](/reference/config#linkbase); without it, `app.open`
  takes no path and a link goes through [`device.openLink`](#openlink).
- `app.appPath` is the build the suite runs against. The engine installs
  nothing on its own: [`device.installApp()`](#installapp) installs it where
  the suite says so. A device provider installs it on the device it leases.
- Without `bundleId`, the installed bundle id or package becomes the app
  `app.open()` launches.
- Declare an `identity` when the build path changes per run (a version in
  it), so recordings survive the rename.

| Throws | When |
| --- | --- |
| `INVALID_CONFIG` | At config load: no `app.bundleId` and no `app.appPath`; an `app.url` (not supported yet); a link in `bundleId` (a test opens one with `device.openLink`); an unknown permission name; an Apple launch argument such as `AppleLocale`, or a list item `am start` cannot carry, in an object on an Android target. |
| `UNSUPPORTED_CAPABILITY` | `app.open()`, `app.restart()`, or `app.clearState()` on a target with no `app.bundleId` before its build is installed. |

#### Launch arguments and permissions

`app.launchArguments` and `app.permissions` ride every fresh launch of the
pinned app: `app.open()`, `app.restart()`, and `app.clearState()`, which
resets the permissions with the data.

```ts title="e2e.config.ts"
export default {
  targets: [
    {
      name: 'pixel',
      engine: mobile({ platform: 'android' }),
      app: {
        bundleId: 'com.example.app',
        launchArguments: ['--ez', 'e2e', 'true'],
        permissions: { camera: 'grant', notifications: 'deny' },
      },
    },
  ],
} satisfies E2EConfig;
```

- iOS hands the arguments to the app process
  (`ProcessInfo.processInfo.arguments`). Android appends them to `am start`,
  so `['--ez', 'e2e', 'true']` is a boolean intent extra.
- An object gives each argument a name.
  - On iOS, each entry becomes `-name value` in the format that
    `NSUserDefaults` reads. A string that the parser could read as a plist or
    a comment, such as `(draft)`, `a b`, or `//cdn`, gets quotes. An app that
    reads `ProcessInfo.processInfo.arguments` receives this format, with `NO`
    for `false` and the quotes included. If your app reads
    `ProcessInfo.processInfo.arguments`, use the list format instead:
    `launchArguments: ['-flag', 'false', '-title', 'a b']`.
  - On Android, each entry becomes an `am start` extra of the value's type.
    The app reads it with the matching `Intent` getter. A whole number such
    as `1.0` is an `int`. Android does not read Apple arguments, so
    `AppleLanguages` or `AppleLocale` in an object on an Android target fails
    with `INVALID_CONFIG`. A list of strings goes to `am start` unchanged.
- On Android, a list in an object fails with `INVALID_CONFIG` when the list
  is empty, or when an item is empty, contains a comma, or ends with a
  backslash.

| Value | iOS | Android |
| --- | --- | --- |
| `'fr_FR'` | `-name fr_FR` | `--es name fr_FR` |
| `'(draft)'` | `-name "(draft)"` | `--es name (draft)` |
| `true` | `-name YES` | `--ez name true` |
| `3` | `-name 3` | `--ei name 3`, `--el` outside Java's `int` |
| `1.5` | `-name 1.5` | `--ef name 1.5` |
| `-1` | `-name "-1"` | `--ei name -1` |
| `['fr', 'de']` | `-name (fr, de)` | `--esa name fr,de` |

- Each permission is `grant`, `deny`, or `reset`. `reset` puts it back to not
  asked for yet, so the OS asks again. `deny` is a recorded
  refusal on iOS, where the app is told no without a prompt, and a revocation
  on Android, where the OS asks again when the app requests the permission.
- `permissions: 'all'` grants every permission the platform can set. It
  replaces the map; name permissions instead to deny or reset one.
  - On Android: each runtime permission the app's manifest declares.
    Permissions that are not grantable at run time, such as `INTERNET`, are
    skipped, so an app that declares none launches with nothing changed.
  - On an iOS simulator: each privacy service the runtime can set, with
    location `always`. The simulator refuses notifications, so accept that
    prompt with `device.alert('accept')`.
- The open in [`prepare`](#boot-and-prepare) passes no launch argument and
  touches no permission.
- [`device.openApp(app, { relaunch: true, launchArguments, permissions })`](#openapp)
  does the same for one launch of any app.

| Throws | When |
| --- | --- |
| `INVALID_CONFIG` | In `app.permissions`: a permission name outside `DevicePermission` (naming the nearest one when it is a likely typo), or a state other than `grant`, `deny`, or `reset`. Fails before any device command. |
| `INVALID_ARGUMENT` | The same, in `device.openApp`. |

#### Boot and prepare

Devices boot in `prepare`, once per run and before the run's clock starts,
so a cold boot on CI is never charged against `launchTimeout`.

- On iOS, `prepare` starts the automation runner on every device.
- Then, on both platforms, it opens the target's `app.bundleId` once per
  device. A build the suite installs itself comes up with the first
  `app.open()`.
- A device that cannot boot, or a runner that is busy, wedged, or past its
  watchdog, ends the run in `prepare`.
- A runner that does not start for another reason is logged and left to the
  first attempt, and that device's app is not opened there.

Each device logs one line of how long its prepare steps took, a failed step
included: `boot`, `iOS runner` (the automation runner's start, on iOS only),
and `open <app>`, which is missing where the open is skipped. A cold iOS
simulator:

```text
ℹ booting E93FA5E5-1592-43C7-9149-F1B5FE0AD5F5 (1 of 1)
ℹ E93FA5E5-1592-43C7-9149-F1B5FE0AD5F5: boot 36.3s, iOS runner 61.6s, open dev.e2e.benchmark 9.2s
```

An ordinary app-open failure is logged on a line of its own,
`<device>: <app> did not open (<reason>); the first attempt opens it`, and
the run goes on.

<Note>
A pending tap, double tap, multi-tap, focus, check or uncheck is cancelled when
the step stops waiting for it or the run is interrupted. Input already sent
to the device may still finish. Other commands can outlive their caller's
timeout; the next attempt waits for them to finish.
</Note>

#### Capabilities

| Contract member | On a device |
| --- | --- |
| `observe` | The accessibility tree with rects. Element types map onto roles as listed under [Roles](#roles); a `Switch` or `CheckBox`, and an Android `RadioButton`, carry the `checked` state the device reports, and a `SecureTextField` or an Android field flagged as `password` is a secure `textbox`. An iOS field keeps a value equal to its label (an unlabeled field is named by its text); Android's echo of a text view's label as its value is dropped. The accessibility identifier (iOS) or resource id (Android) is the node's `testId`. An Android node is named by the content description its app set (React Native's `accessibilityLabel`), or by its text, and its `text` is what it shows, so a labeled text view or a filled field answers `getByLabel` by its label and `getByText` by its text. Nodes also carry `label`, `resource-id`, `class`, and Android `content-desc` attributes (see [`getAttribute`](/reference/screen#getattribute)). A field's hint is its `placeholder` attribute, showing or not. Compose Multiplatform reports no placeholder on iOS: an empty field appends the text it draws to its label (`Name, Ada Lovelace`) over one `StaticText` child, so that text is the field's `placeholder` and the child is left out. An empty field has no value: an iOS field whose value equals its placeholder (trimmed) reads empty, text typed to match the placeholder exactly included. On Android, `rect` and every point are the screen's physical pixels; the display density is not applied yet. Android's status bar and navigation bar are left out; the notification shade, system dialogs, and a heads-up notification or other popup inset from the sides stay. Pixels on request, with every secure node's bounds painted black. |
| `perform` | `tap`, `doubleTap`, `multiTap`, `longPress`, `fill`, `clear`, `hover`, `check`, `uncheck`, `press` (`Enter`, `Space`, or one character), `swipe`, `scrollTo`, `dragTo`, and `focus` on editable fields. `scrollTo` drags the node, or the screen on the root, until the content stops changing. A tap on a `switch` or `checkbox` lands on its innermost control. `check` and `uncheck` need a `checked` state. Switches report one on both platforms, and so does a native Android `CheckBox`; a React Native checkbox or radio reports one only when the app sets `accessibilityState.checked`. A control with no state is `UNSUPPORTED_CAPABILITY`, so tap it instead. `doubleTap` is two presses, 284 to 285 ms apart on iOS. A detector with a window of 300 ms or less can read the pair as two single taps. `multiTap` is `count` presses at the same cadence as `doubleTap`, so the same short-window caveat applies; a `count` above 200 is `UNSUPPORTED_CAPABILITY` before any press. At about 285 ms a press on iOS, 200 presses take about a minute, past the default action timeout of 30 s, so pass a longer `timeout` for a large `count`. `longPress` holds for one second unless the test passes `duration`. `blur`, `selectOption`, `setInputFiles`, `scrollIntoView`, and `secondaryTap` are not declared, and neither is `tapModifiers`, so `tap`, `doubleTap`, or `multiTap` with `modifiers` is `UNSUPPORTED_CAPABILITY`. |
| `performAt` | `tap`, `doubleTap`, `longPress`, and `swipeTo` at a bare screen point, so `screen.tapAt`, `screen.doubleTapAt`, `tap({ position })`, `screen.swipe({ from, to })`, and the agent's `tap_at` reach a control the tree does not list. On iOS, while the soft keyboard is open, a `screen.swipe({ from, to })` with no `duration` has to stay above it, and fails with `ACTION_FAILED` before anything is sent when it doesn't. With `duration` the path goes out as given, across the keyboard, as a test of interactive keyboard dismissal needs. No `hover`, `secondaryTap`, or `dragTo` at a point, so `hover_at` needs a listed control. |
| `keyboard` | `type` and `press` into the focused field, the agent's `type` and `press` without a target and the fallback of `type_at` and `press_at`, and `dismiss`, the agent's `dismiss_keyboard`. |
| `locate` | Every `screen` query. Text and label queries answer with the innermost match. On Android a test id query, a string or a RegExp, also matches a resource id without its `<package>:id/` prefix, for any package but the framework's `android`, when nothing on the screen matches the full id. `screen.locator('id=…')` is agent-device's selector and takes the full id. |
| `validateApp` | Requires `app.bundleId` or `app.appPath` and refuses `app.url` for now, with a note on reaching this machine from the platform's device. |
| `session` | `back`, `restart`, `reset`, and `openLink`, behind `app.open(path)` on a target with `app.linkBase`. No `open`: `app.open()` with no path is served with `restart`, the fresh launch of the pinned app; the agent's `navigate` verb is unavailable, and `device.openLink(url)` opens a deep link or web link. |
| `artifacts` | Redacted screenshots under `screenshots/NNN-<label>.png`; a screenshot that cannot be redacted fails instead of being written. Video, when the attempt's [video mode](/reference/config#video) records, as `video/video.mp4`, or a device provider's own recording. |
| `location` | `<bundle id> / <screen title>`, the replay cache's anchor. The title is the navigation bar's on iOS and the toolbar's on Android. |
| `state` | Not declared. `test.setup` and `session:` are unavailable. |

directly to arrange or assert device state.

```ts
  await app.open();
  await device.setNetwork('offline');

  await device.setNetwork('online');

```

#### `unstable_raw`

```ts
readonly unstable_raw: DeviceSession;
```

```ts
const { client, selection } = device.unstable_raw;
await client.apps.list(selection);
```

`client` is typed as `DeviceSessionClient`, exported from `@e2e-dev/mobile`.
After the worker disposes the session, reading `unstable_raw` or `client`
throws `INVALID_STATE`.

- Use it for what the methods here do not cover.
- Calls through `client` bypass e2e. They are not steps, so the report and
  trace leave them out and the agent's cache does not replay them. Their
  arguments reach the driver unredacted, and nothing waits for the screen to
  settle after one.
- It is unstable: it may change or go away in any release.

#### `locator`

```ts
locator(selector: string): Locator;
```

```ts
await expect(device.locator('role=navigation-bar id=About')).toBeVisible();
await expect(device.locator('role=text label="iOS Version"')).toHaveText('iOS Version');
await device.locator('id=SW_VERSION_SPECIFIER role=button').tap();
```

Use it for a node the `screen` queries cannot name. It polls and is strict
like any locator.

Selector terms and their rules are agent-device's, the ones `agent-device
find ... list` applies:

- Terms: `id`, `role`, `text`, `label`, `value`, `appname`, `windowtitle`,
  and the flags `visible`, `hidden`, `editable`, `selected`, `focused`,
  `enabled`, `hittable`.
- `role` takes agent-device's kind, the role `agent-device snapshot` prints:
  `button`, `text`, `text-field`, `navigation-bar`, `scroll-area`, `switch`,
  `image`. It is not the `getByRole` role (`textbox`).
- Text terms compare case-insensitively after collapsing whitespace.

#### `installApp`


#### `lock`

```ts
lock(): Promise<void>;
```

```ts
try {
  await device.lock();
} finally {
  await device.unlock();
}
await expect(screen.getByText('Welcome back')).toBeVisible();
```

- It resolves once the device reports the screen locked. A screen that is
  already locked stays locked.
- A lock that asks for a PIN, pattern, password, or passcode is locked too,
  but `unlock()` refuses it, so the device stays locked until someone unlocks
  it by hand: use Swipe on Android and no passcode on iOS.

To lock the screen for a time, as Appium's `lock(seconds)` does, wait between `lock()` and `unlock()`.

On an iPhone simulator with an always-on display, such as the iPhone 17 Pro, `unlock()` can leave the display off while the device reports it unlocked. Taps and screen reads still work, but a screenshot shows the last frame before the display went off, and on iOS 26.5 every later `fill` on that simulator fails its read-back for the rest of the run. An iPhone without an always-on display, such as the iPhone 16e, is not affected.

The engine never unlocks the device for you. A test that fails while the screen is locked leaves it locked for the next test on that device, so unlock in a `finally` block or in `afterEach`. Both methods run on the app session: after [`closeApp`](#closeapp) they fail with `APP_NOT_OPEN` until `openApp` opens an app, so unlock before you close the app.

| Throws | When |
| --- | --- |
| `UNSUPPORTED_CAPABILITY` | The device is not one agent-device can lock: a physical iPhone or iPad, an Android TV or Apple TV, or a device a provider drives through its own backend with no lock command. |
| `UNSUPPORTED_CAPABILITY` | The Android device's screen lock is set to None, on Android 16 or newer. The message says so; set any other screen lock, such as Swipe, in Settings > Security. |
| `ACTION_FAILED` | `actionTimeout` expired before the device reported the screen locked. On an Android device with a PIN, pattern, or password and "Power button instantly locks" off, the keyguard waits for "Lock after screen timeout", up to one minute; raise `actionTimeout` or turn that setting on. |
| `ENGINE_FAILURE` | The device did not report the screen locked: on Android within 5 seconds, plus the "Lock after screen timeout" delay up to one minute. On Android 11 to 15 with the screen lock set to None, this is the failure, with the message `still reports the keyguard hidden`, and the display is left off. |
| `ENGINE_FAILURE` | Android 10 or older, on an unlocked screen: agent-device cannot read the lock type (`Unable to read the screen lock type`), and no key is sent. |

### Agent tools

`mobileTools(...engines)` from `@e2e-dev/mobile/tools` adds device tools to
an agent's `tools`.

```ts
tools: mobileTools(iphone, pixel),
```

- It takes at least one engine. Pass all device engines in one call; the
  tools use the current attempt's engine.

| Tool | Replay | Purpose |
| --- | --- | --- |
| `open_app` | gap | Bring an app to the foreground by id, optionally relaunched. Without an id it returns to the target's app. A link is refused, as it is for `device.openApp`. |
| `swipe` | gap | Free-form swipe between two points in logical pixels. |
| `alert` | gap | Accept or dismiss a system alert; prefer a listed button, whose tap replays. |

`tvTools(...engines)` adds the TV remote for engines that drive an Android TV
or an Apple TV. It is a pack of its own, so a config with no TV offers no
remote.

```ts
tools: { ...mobileTools(tv), ...tvTools(tv) },
```

Tools are offered by platform. When a phone target shares the TV's platform,
put `tvTools` on a [named agent](/reference/config#agents) and select it on
the TV tests.

| Tool | Replay | Purpose |
| --- | --- | --- |
| `tv_remote` | gap | Press a [remote button](#pressremote) by `key`, up to 20 `times` in one call. |

`foldTools(...engines)` adds the hinge for engines that drive a foldable: the
iPhone Duo simulator or a foldable Android emulator. With it in the agent's
`tools`, `agent.act`, `e2e explore`, and the MCP server's `call` can fold the
device.

```ts
tools: { ...mobileTools(iphoneDuo), ...foldTools(iphoneDuo) },
```

- Tools are offered by platform, as with `tvTools`. When a device without a
  hinge shares the foldable's platform, put `foldTools` on a
  [named agent](/reference/config#agents) and select it on the foldable
  tests.
- The engine never resets the pose, so a pose the agent leaves carries over
  to the next test. Fold back in `afterEach`, as for
  [`device.fold`](#fold).

| Tool | Replay | Purpose |
| --- | --- | --- |
| `fold` | gap | Put the device in a hinge [`pose`](#fold): `closed`, `half-open`, or `open`. A device without a hinge fails with `UNSUPPORTED_CAPABILITY`. |

| Throws | When |
| --- | --- |
| `INVALID_STATE` | An engine that `mobile()` did not return. In the config this fails the load as `CONFIG_LOAD_FAILED`, whose message includes this one. |

A tool that fails during a built-in agent step returns
`Tool "<name>" failed: <message>` to the model as the call's result; the step
goes on. `open_app` fails with `INVALID_STATE` when it names no app, the
target has no `app.bundleId`, and nothing has installed its `app.appPath`
build yet (no `device.installApp()`, no device provider install); with
`INVALID_ARGUMENT` when it names an app that is not installed or a link; and
with `POLICY_DENIED` for a link with a forbidden scheme. Any tool fails with
`INVALID_STATE` when no device attempt is running, or when several device
attempts are running in one worker.

The grammar verbs need no tool pack. The engine's declared actions give the
agent:

- `tap`, `double_tap`, `long_press`, `hover`, `type`, `press`, `check`,
  `scroll`, `drag`, `scroll_to` by `text` (paging the list until a row
  reading it is drawn), `back`, and `dismiss_keyboard`.
- The pixel tools `screenshot`, `tap_at`, `hover_at` (on a listed control
  only), `drag_at` (between two different listed controls only), `type_at`, and
  `press_at`. Point actions can tap controls absent from the accessibility
  tree.
- `type_secret`, which fills only a secret the step declares.

There is no `right_click`, `select`, `scroll_to` by node id, `upload`, or
`navigate` on a device, and `select_at` is not offered.

<Note>
Pixels whose masking the engine cannot prove are withheld as `MASKING_UNPROVEN`. An accessibility
capture failure still stops the observation.
</Note>

#### `unstable_deviceSession`

`unstable_deviceSession(...engines)` from `@e2e-dev/mobile/tools` gives a custom tool
the running attempt's `DeviceSession`, the same object a test reads from
[`device.unstable_raw`](#unstable_raw), for capabilities e2e does not wrap
yet. Its `client` is typed as `DeviceSessionClient`.
The following example assumes the current driver supports `settings.update`.

```ts
import { tool } from 'ai';
import { z } from 'zod';
import { defineTool } from 'e2e/agent';
import { unstable_deviceSession } from '@e2e-dev/mobile/tools';

const mobileData = defineTool(
  tool({
    description: 'Turn cellular mobile data on or off. Wi-Fi is not affected.',
    inputSchema: z.object({ on: z.boolean() }),
    execute: async ({ on }) => {
      const { client, selection } = unstable_deviceSession(iphone, pixel);
      await client.settings.update({ ...selection, setting: 'mobile-data', state: on ? 'on' : 'off' });
      return on ? 'mobile data is on' : 'mobile data is off';
    },
  }),
  { mutates: true, platforms: ['android'] },
);

tools: { ...mobileTools(iphone, pixel), mobileData },
```

- Pass every device engine the config declares, as with `mobileTools`.
  Outside an attempt it throws `INVALID_STATE`.
- Spread `selection` into a call so it reaches the worker's device even
  before the session has an app open, as the engine's own calls do.
- Client calls are not steps: the report shows the tool call, not what the
  client did, and a cache replay runs a `mutates: true` tool live.
- Client calls skip e2e's guards, as with `unstable_raw`. A snapshot or
  screenshot a tool returns is not redacted or masked, even after a secret
  fill, nothing waits for the screen to settle after a call, and a tool
  whose calls change the device must declare `mutates: true`.
- Like `unstable_raw`, it can change in any release.

## Roles

`getByRole` on a device matches the role each element type maps to. A type
not listed keeps its own name in lower kebab case (`picker-wheel`), so it
matches a `getByRole` role only when that name is one (`group`, `table`).
A node the platform reports editable is a `textbox`, unless it already maps
to `combobox`.

| --- | --- | --- |
| `button` | `Button` | `Button`, `ImageButton`, `MaterialButton` |
| `link` | `Link` | |
| `textbox` | `TextField`, `SearchField`, `TextView`, `SecureTextField` | `EditText`, `AutoCompleteTextView`, `TextInputEditText`, `SearchView` |
| `combobox` | | `Spinner` |
| `switch` | `Switch`, `Toggle` | `Switch`, `SwitchCompat`, `SwitchMaterial`, `ToggleButton` |
| `checkbox` | `CheckBox` | `CheckBox`, `MaterialCheckBox` |
| `radio` | `RadioButton` | `RadioButton` |
| `radiogroup` | `RadioGroup` | `RadioGroup` |
| `slider` | `Slider` | `SeekBar`, `Slider` |
| `spinbutton` | `Stepper` | `NumberPicker` |
| `progressbar` | `ProgressIndicator` | `ProgressBar` |
| `status` | `ActivityIndicator` | |
| `image` | `Image`, `ImageView` | `ImageView` |
| `heading` | `Heading`, `Header` | A view flagged as a heading |

React Native writes a role the platform has no type for into the
accessibility value on iOS (`checkbox, unchecked`) and into the role
description on Android (`Tab List`). A node with one of these descriptions
takes the role in place of its type's: `alert`, `checkbox`, `combo box`,
`menu`, `menu bar`, `menu item`, `progress bar`, `radio button`,
`radio group`, `scroll bar`, `spin button`, `switch`, `tab`, `tab list`,
`timer`, and `tool bar`. The `scrollbar` and `timer` roles that `scroll bar`
and `timer` give are not `getByRole` roles.
On iOS only an `Other` carries one, and the state words after the role set
`checked` and `expanded`; only what follows them is the node's value.

`StaticText` and `Text` on iOS and `TextView` on Android are `text`, and an
Android `WebView` is `document`. Neither is a `getByRole` role: find text
with `getByText`.

## Visibility

A device node is hidden when the platform reports it off screen, or when the
soft keyboard covers its centre. So `toBeVisible()`, `scrollUntilVisible`,
and `getByRole` treat a field under the keyboard like a field scrolled out
of view. The keyboard's own keys, suggestion bar, and dock stay visible, and
so does the focused field.

- A container whose centre is under the keyboard stays visible while one of
  its children shows above it.
- A node under another view, such as a footer the keyboard lifts, is not
  hidden. A tap on it fails with `ACTION_FAILED` when agent-device finds the
  cover, and the message names the cover. A tap under the keyboard fails the
  same way. Dismiss the cover, or scroll the target clear of it.

## Video recording cleanup

If a recording fails to stop, cleanup retries the stop. For a device
provider's recording the retries come at attempt end, before another attempt
on that worker, and during worker disposal. The next attempt starts only
after the provider confirms the stop; a failed or cancelled stop wait
prevents that attempt from starting.

A recording recovered by a retry is not added to the report: its file can
stay in the original attempt's video directory, and a returned URL is
dropped. A required video whose first stop failed stays a cleanup failure.

Recording handles do not survive worker exit. Providers must clean up any
remaining external recordings when releasing a lease: closing an
agent-device session cannot guarantee that a cloud recording stops, and a
failed stop callback does not confirm that the recording stopped.

## Replay cache on a device

The replay cache anchors on the [`location`](#capabilities) a device reports,
`<bundle id> / <screen title>`. A step recorded on
`com.apple.Preferences / General` replays only when Settings is on General
again.

```ts
await app.open();
await screen.getByText('General').tap();
await agent.act('Open About and read the iOS version');
```

- A mutating project-tool call such as `open_app` ends a replay.
- Declare `app.bundleId` and call `app.open()` first, so steps start on the
  same screen.
- Switch apps through the `device` fixture between steps rather than inside
  one.
- A step recorded after [`device.openLink`](#openlink) replays when the link
  lands on the same screen again.
