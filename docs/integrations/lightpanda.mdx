[Lightpanda](https://lightpanda.io) is an open-source headless browser
written from scratch, without Chromium. It starts in milliseconds, holds a
fraction of Chrome's memory, and speaks the Chrome DevTools Protocol.
`lightpanda()` from `@e2e-dev/lightpanda` is a
[browser provider](/browser#hosted-browsers) for it: each worker slot gets
its own `lightpanda serve`, started on a free port when the run starts and
stopped when it ends.

<Note>
The web engine cannot open a page in Lightpanda. A test that opens one times
out. See [What does not work](#what-does-not-work).
</Note>

## Setup

Install the package:

<CodeGroup>
```bash npm
npm install --save-dev @e2e-dev/lightpanda
```

```bash pnpm
pnpm add -D @e2e-dev/lightpanda
```

```bash bun
bun add -d @e2e-dev/lightpanda
```
</CodeGroup>

And the Lightpanda nightly binary, which the provider starts:

<CodeGroup>
```bash macOS
brew install lightpanda-io/browser/lightpanda
```

```bash Linux
curl -L -o lightpanda https://github.com/lightpanda-io/browser/releases/download/nightly/lightpanda-x86_64-linux
install -D -m 755 lightpanda ~/.local/bin/lightpanda
```
</CodeGroup>

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';
import { lightpanda } from '@e2e-dev/lightpanda';

export default {
  targets: [
    {
      name: 'lightpanda',
      engine: web({ browser: lightpanda() }),
      app: { url: 'http://localhost:3000' },
    },
  ],
} satisfies E2EConfig;
```

The provider runs `lightpanda` from `PATH`, `~/.lightpanda/lightpanda`, or
`~/.local/bin/lightpanda`, the places
[agent-browser](https://agent-browser.dev/engines/lightpanda) looks too, or
the binary `LIGHTPANDA_PATH` names in the environment `e2e run` starts in,
or `binary` in the options. None found fails the run before any test,
naming the install page.
Each worker gets its own server, so `workers` sets how many run at once,
and the run's log names each one:

```text
ℹ lightpanda (1 of 2): lightpanda 1.1.0-nightly at ws://127.0.0.1:51165/
```

## Attach to a running server

A Lightpanda already running, such as the Docker image in CI, is a
[`connect`](/reference/web#options) target rather than a provider: the
engine attaches to its CDP endpoint and leaves it running.

```ts title="e2e.config.ts"
web({ connect: { cdpEndpoint: () => process.env.LIGHTPANDA_URL ?? 'ws://127.0.0.1:9222/' } })
```

```bash
docker run -d --name lightpanda -p 127.0.0.1:9222:9222 lightpanda/browser:nightly
```

Every worker then shares that server. One `lightpanda serve` takes 16
connections by default; raise its `--cdp-max-connections` above `workers`
when you run more.

## Options

| Option          | Default                         | Meaning |
| --------------- | ------------------------------- | ------- |
| `binary`        | `LIGHTPANDA_PATH`, else found   | The binary to start: a path, or a name on `PATH`. |
| `loadResources` | `['stylesheet']`                | Sub-resources the server fetches: `iframe`, `image`, `stylesheet`. See [Fetch more of the page](#fetch-more-of-the-page). |
| `args`          | `[]`                            | Further `lightpanda serve` flags, after the ones the provider sets. |

The provider leases one server per worker slot for the run. A server that does not answer
on its port within ten seconds fails the lease, and so does a binary that
exits first, with its stderr in the message.

## Fetch more of the page

`lightpanda serve` requests no sub-resources by default: no images, no
external stylesheets, no iframes. The provider asks for stylesheets, and
`loadResources` sets the list, as `--load-resources` on the server. A list
replaces that default, so keep `stylesheet` in it, and `[]` fetches none:

```ts
web({ browser: lightpanda({ loadResources: ['stylesheet', 'iframe'] }) })
```

## What works

Only what needs no page works. On a Lightpanda nightly from November 2026
(`1.1.0-nightly.12226`), the e2e testbed's local suite gets this far:

- The provider starts one server for each worker slot and stops it when the
  run ends.
- A test that opens no page passes, such as one that calls an API with
  `fetch`.

## What does not work

No test that opens a page passes, with the provider or with
[`connect`](#attach-to-a-running-server). Every query, action, assertion,
and [agent step](/agent-steps) needs a page.

| Feature | What happens | Why |
| ------- | ------------ | --- |
| Opening a page: `app.open`, `browser.goto` | The call never returns. The test fails when its [`timeout`](/reference/config#timeout) ends, with `TEST_TIMEOUT` or `ACTION_FAILED`. | Lightpanda does not report a new page the way the engine reads it. |
| [Sessions](/authentication) (`test.setup` with `session.save`, `session:` on a test) | The setup times out the same way, and e2e skips each test that uses its session. | The setup cannot open a page. |

A fix needs changes in Lightpanda. Run the suite on a Chromium target
instead.
