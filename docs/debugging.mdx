A failed test prints its error and the path to its trace page. Work through
the steps below in order and stop at the one that explains the failure.

## Read the failure

The `list` reporter's `Failed Tests` section shows the error, the failing
line, nearby matches for a failed locator, what the app logged, and the
trace page:

```text
 FAIL  |web| tests/todos.e2e.ts > shows the remaining count
LOCATOR_NOT_FOUND: locator did not become visible: getByRole("heading", name: "Todos")
 ❯ tests/todos.e2e.ts:31:3
 ❯ at http://127.0.0.1:4271/nope
 ❯ app 2 errors, 2 warnings logged
   × console error: Error occurred prerendering page "/todos"
   × network error: GET /api/todos 500 Internal Server Error
 ❯ trace .e2e/results/todos-shows-the-remaining-count-796fac5f12ab34cd/trace.md
```

The error code names the cause, and
[Common errors](/reference/errors#common-errors) has the usual cause and fix
for each one. The [exit code](/reference/errors#exit-codes) tells the type
of failure and whether a retry can help.

For a summary of the whole run, add the
[`markdown`](/reference/reporters#markdown) reporter, which writes
`.e2e/summary.md`. A script reads the same facts from
[`report.json`](/reference/reporters#report-json).

## Open the trace page

By default, each failed, timed out, interrupted, or flaky test gets a trace
page, `trace.md`, in its directory under `.e2e/results/`. Open it in an
editor's markdown preview so its links work. It lists every step with what
it did, then the app log, the agent's last turns, and the screen at failure.

<Accordion title="Example trace page">

````markdown

**ASSERTION_FAILED**

```text
expect.toHaveText failed
locator: getByRole("status", name: "Remaining")

observed: text "0 remaining" (match count 1)
````

## Look at the screen and the app log

The **Screen at failure** section has the screenshot and the semantic tree
the test saw. Compare them with the locator or the expectation that failed.

The **App log** section has the app's console output, uncaught exceptions,
and failed requests, each with its step. Check it when an assertion read the
same wrong value the whole time: a failed request often explains it. An
assertion whose readings changed raced the app.

<a id="artifacts" /><a id="console-output" />

The screenshot, any video, and downloads are files in the test's directory.
[What a run captures](/reference/config#what-a-run-captures) lists them. A
`console.log` in the test prints while it runs, under a
[heading that names the test](/reference/reporters#console-output).

## Watch it happen

Rerun the test with a visible browser. Add `--video` to record the run.

<CodeGroup>
```bash npm
npx e2e run tests/todos.e2e.ts --headed
```

```bash pnpm
pnpm exec e2e run tests/todos.e2e.ts --headed
```

```bash bun
bunx e2e run tests/todos.e2e.ts --headed
```
</CodeGroup>

Each recording goes into its attempt's directory, and the failure recap
prints its path. In CI, set `video: 'on-first-retry'` in the config. A test
that passes the first time records nothing, and a flaky test leaves a
recording of its retry.

[Recording](/reference/config#recording) has every mode, which setting wins,
and what happens on an engine that can't record.

## Step through a test

`--step` runs the first step, then holds each later step until you press a
key. Add `--headed` to watch the browser between steps.

<CodeGroup>
```bash npm
npx e2e run tests/checkout.e2e.ts --step --headed
```

```bash pnpm
pnpm exec e2e run tests/checkout.e2e.ts --step --headed
```

```bash bun
bunx e2e run tests/checkout.e2e.ts --step --headed
```
</CodeGroup>

At the prompt, Enter runs the held step, `s` shows the screen, `l` shows the
app log, and `q` stops the run. Paused time doesn't count against step,
test, or run timeouts. [Step mode](/reference/cli#step-mode) lists every key and what runs
without pausing.

<a id="step-through-a-test-without-a-terminal" />

Without a terminal, as in a coding agent's shell, `--step` runs the test in
the background and returns at the first held step with its screen. Run
`e2e run --step next` for each later step, `--step rest` to run the rest, or
`--step stop` to end the run. See
[Step commands](/reference/cli#step-commands).

## Pause a test

With [`screen.pause()`](/reference/screen#screen-pause), you can pause the
test at a line, with the app open, until you resume it. The test is paused
each time the line runs, such as on every pass of a loop.

```ts title="tests/checkout.e2e.ts"
import { test } from '@e2e-dev/web';

test('pays with a card', async ({ app, screen }) => {
  await app.open('/checkout');
  await screen.pause();
});
```

Run the test with `--headed` to look at the browser while it's paused. Press
Enter to resume, or `s` and `l` for the screen and the app log, as at a
`--step` prompt. Without a terminal, resume with `e2e run --step next` from
another shell in the same directory. In CI, `screen.pause()` fails the test
immediately, so remove it before committing.

## Check what the model was sent

Rerun an `agent.act` or `agent.assert` step live and record what the agent
did:

<CodeGroup>
```bash npm
npx e2e run tests/todos.e2e.ts --no-cache --debug --ai-trace
```

```bash pnpm
pnpm exec e2e run tests/todos.e2e.ts --no-cache --debug --ai-trace
```

```bash bun
bunx e2e run tests/todos.e2e.ts --no-cache --debug --ai-trace
```
</CodeGroup>

`--debug` prints a table with one row per agent step: duration, model
calls, tokens, prompt-cache share, and cost when the provider reports one.
See [Debug output](/reference/cli#debug-output).

`--ai-trace` writes `.e2e/ai-trace.json` with every model call. Read it with
unbox-ai, as [Output](/reference/cli#output) shows, to see the prompts and
tool calls. A replayed step makes no model call and leaves no AI trace, so
`--no-cache` traces the whole flow and rules out a stale
[recording](/cache). [Agent steps](/agent-steps) explains what the model
sees and may do.
