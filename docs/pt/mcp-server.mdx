`e2e mcp` dá a um agente de código, como Claude Code, Codex ou Cursor, uma
sessão ao vivo no seu app, na web, no iOS ou no Android. O agente vê a tela,
age sobre ela e verifica o próprio trabalho.

## Por que isso importa

| Tarefa | Sem `e2e mcp` | Com `e2e mcp` |
| --- | --- | --- |
| Escrever um teste | Adivinha localizadores, roda, falha, adivinha de novo | Escreve o teste enquanto percorre o fluxo, a partir de linhas de teste verificadas e de linhas que rodou com `run_code` |
| Mudar a UI | Pronto quando compila | Abre a página e verifica o resultado |
| Reproduzir um bug | Adivinha a partir do código | Segue os passos no app |
| Corrigir um teste que falha | Percorre o fluxo clicando de novo | Roda o teste e fica parado na falha |
| Mostrar uma mudança em um PR | Descreve a mudança | Grava um vídeo |

O servidor MCP em si não precisa de um modelo. Você só precisa de um se
rodar um teste com um passo do agente sem cache.

## Configure

O [plugin do e2e](/coding-agents) para Codex e Cursor inclui o servidor
como `npx -y e2e@<version> mcp`, que roda a release do e2e do plugin mesmo
quando o projeto tem outra versão instalada. No Claude Code (ou sem o
plugin), registre o servidor no seu projeto. O `e2e init` pode escrever a
configuração para `.mcp.json` (Claude Code), `.cursor/mcp.json` (Cursor) e
`.codex/config.toml` (Codex), com o comando do seu gerenciador de pacotes:
`npx e2e mcp`, `pnpm exec e2e mcp`, `yarn exec e2e mcp`
(`yarn --silent exec -- e2e mcp` no Yarn 1) ou `bunx e2e mcp`. Instale as
dependências do seu projeto e inicie o seu cliente MCP no diretório do
projeto para que o comando use a versão instalada do `e2e`. Para configurar
manualmente:

<Tabs>
  <Tab title="Claude Code">
    <CodeGroup>
    ```bash npm
    claude mcp add --scope project e2e -- npx e2e mcp
    ```

    ```bash pnpm
    claude mcp add --scope project e2e -- pnpm exec e2e mcp
    ```

    ```bash bun
    claude mcp add --scope project e2e -- bunx e2e mcp
    ```
    </CodeGroup>
  </Tab>
  <Tab title="Codex">
    Rode `e2e init --yes --skills none --mcp .codex/config.toml` com a CLI
    instalada, ou adicione a entrada abaixo. Marque o projeto como confiável
    e inicie uma nova sessão do Codex. `codex mcp list`, rodado no projeto,
    mostra o registro:

    ```toml title=".codex/config.toml"
    [mcp_servers.e2e]
    command = "npx"
    args = ["e2e", "mcp"]
    ```
  </Tab>
  <Tab title="Cursor">
    Adicione o servidor ao `.cursor/mcp.json`. Outros clientes que leem um
    mapa `mcpServers` aceitam o mesmo bloco.

    ```json title=".cursor/mcp.json"
    {
      "mcpServers": {
        "e2e": { "command": "npx", "args": ["e2e", "mcp"] }
      }
    }
    ```
  </Tab>
  <Tab title="OpenCode">
    Adicione o servidor ao `opencode.json` do projeto. `opencode mcp list`,
    rodado no projeto, mostra o servidor como conectado:

    ```json title="opencode.json"
    {
      "$schema": "https://opencode.ai/config.json",
      "mcp": {
        "e2e": { "type": "local", "command": ["npx", "e2e", "mcp"] }
      }
    }
    ```
  </Tab>
</Tabs>

Se o cliente informar `Connection closed` e o comando falhar em um terminal
com `EBADDEVENGINES`, o `devEngines` do projeto fixa outro gerenciador de
pacotes: registre o comando desse gerenciador, como `pnpm exec e2e mcp`.

Se o seu alvo define um `app.command`, a sessão inicia o seu app e imprime a
URL e a porta do app. A primeira sessão em um arquivo de configuração inicia
os [serviços](/services) desse arquivo, e a última a fechar encerra esses
serviços. A configuração lê o ambiente do servidor MCP, não o shell do seu
agente.

## Experimente sem uma configuração

Se o diretório ainda não tem um `e2e.config.ts`, o agente pode mesmo assim
abrir uma sessão indicando a engine diretamente:

```txt
open_session {engine: "@e2e-dev/web", app: {url: "http://localhost:3000"}}
```

`e2e run` continua exigindo um arquivo de configuração. Para opções da
engine, provedores de dispositivos e a instalação de engines, veja
[Sem uma configuração](/reference/mcp#without-a-config).

## Peça ao agente

- “Adicione um checkbox Lembrar de mim ao formulário de login. Verifique-o no
  app com o e2e.”
- “Escreva um teste para o checkout enquanto você o percorre no app.”
- “Reproduza a issue #123 no app e grave um vídeo.”

Adicione “headed” para assistir a um navegador ou simulador local.

## Como ele escreve uma linha de teste

Cada ação em uma sessão responde com a linha de teste que a repete. O
localizador da linha correspondeu somente àquele controle na tela ao vivo:

```text wrap
Tapped #n31.
Test line: await screen.getByRole("button", "Sign in").tap();
```

O agente copia as linhas de que precisa para o teste enquanto percorre o
fluxo. `test_lines` devolve todas as linhas até o momento, em ordem, com
orientações conforme a sessão seja uma gravação nova, um teste retomado ou
uma sessão conectada a um teste pausado. Veja [`test_lines`](/reference/mcp#test_lines)
para saber como uma linha é montada.

## Como ele verifica um localizador

Para uma linha que nenhuma ação imprimiu, como uma asserção, o agente testa o
localizador na sessão primeiro. Um palpite errado falha ali, não em uma
execução de teste:

```text wrap
0 nodes match getByLabel("Email").
A test using this locator would fail with LOCATOR_NOT_FOUND. ...

1 node matches getByRole("button", name: "Sign in").
Use: screen.getByRole("button", "Sign in")
```

## Como ele roda código

O agente roda JavaScript na sessão aberta com `run_code`: um loop sobre uma
lista, um valor lido e usado em um cálculo, uma asserção que nenhuma ação
imprimiu. Uma chamada substitui muitas ações isoladas:

```js
const rows = screen.getByRole('listitem');
const names = await rows.allTextContents();
await rows.nth(names.findIndex((name) => name.includes('Mug'))).getByRole('button', 'Add').tap();
await expect(screen.getByRole('status')).toHaveText('1 item in cart');
return names.length;
```

As linhas que passam entram no rascunho de `test_lines`. Uma linha errada falha
em segundos, sem uma execução de teste:

```text wrap
Failed: LOCATOR_NOT_FOUND: locator matched no nodes within getByRole("button", name: "Save")
Test lines: 2, 1 failed.
1. await screen.getByLabel('Full name').fill('Grace Hopper');
2. failed: await screen.getByRole('button', 'Save').tap();
   LOCATOR_NOT_FOUND: locator matched no nodes within getByRole("button", name: "Save")
```

O código é JavaScript comum, com os mesmos objetos que o corpo de um teste
recebe. Veja [`run_code`](/reference/mcp#run_code).

## Corrija um teste que falha

`open_session {test: "tests/checkout.e2e.ts:12"}` roda um teste na sessão e
fica parado na tela onde ele falhou. O agente lê a falha, verifica a tela e edita o
teste:

```text wrap
Test "a member checks out" (tests/checkout.e2e.ts:12) failed after 30.25s; 8 steps ran.
LOCATOR_NOT_FOUND: locator matched no nodes within getByLabel("Name")
At tests/checkout.e2e.ts:20:3
On screen, closest to what the locator asked for:
  #n32 textbox "Full name"
```

Cada ação a partir dessa tela imprime sua
[linha de teste](#how-it-writes-a-test-line), e `run_code` roda ali uma linha
corrigida. O agente coloca essas linhas no teste no lugar da que falhou.

Para rodar de novo o teste editado, o agente fecha a sessão e abre uma nova
com o mesmo `test`. Os passos do agente são reproduzidos do cache, como no
`e2e run`. Veja [Rodar um teste](/reference/mcp#running-a-test) para saber o
que roda e quais são os limites.

## Rode testes ao lado de uma sessão

Uma sessão interativa não escreve relatórios de teste, e só os testes
iniciados via `open_session {test}` usam o cache de replay. O seu agente pode
manter uma sessão aberta enquanto roda suítes com `e2e run` e ir direto para
qualquer tela de falha depois.

Na web, se o `e2e run` pode rodar ao lado de uma sessão aberta depende da sua
configuração de `app`:

| `app` do alvo | Rodar `e2e run` enquanto uma sessão está aberta |
| --- | --- |
| Sem `command` | Os dois compartilham o servidor que você mesmo iniciou. |
| `url` na porta [`0`](/web#let-the-runner-pick-the-port) | Cada um inicia sua própria instância do servidor (observe que servidores como o `next dev` não permitem duas instâncias no mesmo diretório). |
| `command` com [`reuseExisting: true`](/web#starting-your-app) | A execução de testes reutiliza o servidor da sessão. Fechar a sessão encerra esse servidor. |
| `command` em uma porta fixa sem `reuseExisting` | Falha porque a porta já está em uso. |

Na CI, o e2e ignora `reuseExisting`, então uma porta fixa se comporta como na
última linha. Feche a sessão antes de rodar os testes se eles forem disputar
com ela a porta ou o dispositivo mobile.

## Rode vários agentes

Cada agente, incluindo subagentes, abre sua própria sessão com seu próprio
navegador ou dispositivo, até quatro por padrão. No mobile, dê a cada sessão
seu próprio alvo.

## Segredos

`type_secret`, ou um `fill` em `run_code`, preenche um segredo sem mostrá-lo
ao agente. As capturas de tela mascaram apenas campos seguros, então um
segredo que o app mostra em qualquer outro lugar aparece nelas.

<Warning>
Os vídeos de `start_recording` não são mascarados.
</Warning>
