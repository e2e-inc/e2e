Um servidor de engine responde ao [protocolo de engine](/reference/engine-protocol)
fora do processo do runner: em um processo filho, em outra máquina ou em um
dispositivo, escrito em qualquer linguagem. `connectEngine` transforma um
servidor em um handle de engine, e o runner controla esse handle como qualquer
outra engine.

## Conecte-se a um servidor

Defina um handle de `connectEngine` como a engine do alvo. O manifesto diz a
que o servidor responde; o runner precisa do manifesto no carregamento da
configuração, antes de qualquer servidor iniciar.

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { connectEngine, spawnTransport } from 'e2e/engine';

export default {
  targets: [
    {
      name: 'kiosk',
      engine: connectEngine({
        manifest: {
          name: 'kiosk',
          version: '1.0.0',
          spiVersion: 1,
          platform: 'kiosk',
          methods: ['engine/observe', 'engine/perform'],
          actions: ['tap'],
        },
        transport: spawnTransport({ command: './kiosk-engine' }),
        resolveLocators: true,
      }),
    },
  ],
} satisfies E2EConfig;
```

- O manifesto que o servidor envia em `initialize` precisa ser igual ao
  declarado. Quando difere, a primeira conexão falha com `ENGINE_FAILURE` e
  nomeia cada campo.
- Com `resolveLocators`, o cliente resolve os localizadores sobre cada
  observação, então um servidor só precisa produzir uma árvore.
- `spawnTransport` inicia um servidor por conexão. `socketTransport` alcança
  um servidor que já escuta em uma porta.

<Warning>
Um servidor recebe o que uma engine no processo do runner receberia: o
ambiente da execução, incluindo as chaves de modelo e os valores
`E2E_SECRET_*`, e os segredos em texto puro. Conecte-se apenas a um servidor
em que você confia, por um canal em que você confia. `socketTransport` não
criptografa.
</Warning>

## Mantenha o trabalho do host no cliente

Alguns membros contêm funções ou precisam da máquina em que o runner está.
Passe esses membros para `connectEngine`; eles rodam no processo do runner:

| Opção | Roda no cliente |
| --- | --- |
| `fixtures` | Factories de fixtures, como uma fixture `device`. Elas chegam ao servidor pelos membros da engine. |
| `validateApp` | A verificação do app no carregamento da configuração. |
| `secrets` | As referências de `secrets.get()` que o servidor pode resolver. |
| `session` | Hooks de sessão que substituem os do servidor, como iniciar um app de novo com `simctl`. |

```ts
const engine = connectEngine({
  manifest,
  transport,
  session: { restart: (operation) => relaunch(operation) },
  fixtures: {
    device: (context) => context.fixture('device', { back: () => engine.session!.back!(context.operation()) }, { back: { kind: 'resource' } }),
  },
});
```

## Sirva uma engine TypeScript

`serveEngine` responde ao protocolo com uma engine de `defineEngine`, por
stdin e stdout por padrão. Rode o servidor como o comando de um
`spawnTransport` e declare o manifesto da engine com `describeEngine`.

```ts title="server.ts"
import { serveEngine } from 'e2e/engine';
import { kiosk } from './src/index.ts';

await serveEngine((options) => kiosk(options as { host: string }));
```

```ts title="e2e.config.ts"
import type { E2EConfig } from 'e2e';
import { connectEngine, describeEngine, spawnTransport } from 'e2e/engine';
import { kiosk } from './src/index.ts';

export default {
  targets: [
    {
      name: 'kiosk',
      engine: connectEngine({
        manifest: describeEngine(kiosk({ host: 'localhost' })),
        transport: spawnTransport({ command: 'node', args: ['server.ts'] }),
        initializationOptions: { host: 'localhost' },
      }),
    },
  ],
} satisfies E2EConfig;
```

Mantenha os logs do próprio servidor no stderr, já que o stdout carrega o
protocolo. Se o servidor terminar inesperadamente durante uma requisição, o
e2e informa o código de saída ou o sinal junto com as últimas linhas do
stderr. (Garanta que os processos filhos que o seu servidor inicia não herdem
o stdout, ou as requisições vão ficar travadas esperando esses processos
terminarem.)

## Escreva um servidor em outra linguagem

Um servidor lê e escreve mensagens JSON-RPC 2.0, cada uma depois de um
cabeçalho `Content-Length`, como faz um language server. Ele responde a:

1. `initialize`, com `{ protocolVersion: 1, manifest }`. Recuse qualquer outra
   versão do protocolo.
2. Cada método que o manifesto do servidor lista, como `engine/observe`. Os
   parâmetros do método são os argumentos do membro, por nome.
3. `shutdown` e, em seguida, a notificação `exit`, depois da qual o servidor é
   encerrado.

Ignore as notificações que você não conhece. Informe uma falha como o erro
`-32000`, com o erro do e2e em `data`, para que o runner a classifique como a
falha de uma engine local. A
[referência das mensagens](/reference/engine-protocol#messages) lista o
formato dos parâmetros e do resultado de cada mensagem. O JSON Schema do
manifesto é distribuído como `schema/engine-manifest-v1.schema.json` no pacote
`e2e`.

## Escreva um transporte

Escreva um transporte quando um servidor precisa de uma preparação antes, como
um app instalado em um dispositivo e uma porta redirecionada para o
dispositivo. `open` recebe o app do alvo, porque um servidor em outro lugar
não consegue ler os arquivos do projeto. Uma conexão `doctor`, que
`e2e doctor` abre, só faz verificações: pule a instalação nela.

```ts
import type { EngineTransport } from 'e2e/engine';

export function deviceTransport(serial: string): EngineTransport {
  return {
    label: `device ${serial}`,
    async open(context) {
      if (context.role !== 'doctor' && context.app?.appPath !== undefined) {
        await install(serial, context.app.appPath);
      }
      const socket = await forward(serial, context.signal);
      return { input: socket, output: socket, close: async () => void socket.destroy() };
    },
  };
}
```
