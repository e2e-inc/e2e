O cache de replay salva as ações de um passo `agent.act()` que passou assim
que uma verificação posterior confirma o resultado. Nas próximas execuções, o
e2e reproduz essas ações sem nenhuma chamada ao modelo. Se a UI mudou e um
elemento ou o estado final esperado não corresponde mais, o agente assume a
partir da tela atual. Veja [Testes com autocorreção](/self-healing).

`agent.assert`, `agent.waitFor` e `agent.extract` sempre rodam ao vivo.
O resumo da execução detalha o que aconteceu com os seus passos `agent.act`:

```text
           AI  4.1k tokens · 2 model calls · openai/gpt-6-luna-fast
        Cache  4 replayed · 1 handed off · 1 missed · 1 not saved
```

`not saved` conta os passos que passaram sem salvar uma gravação, geralmente
porque nenhuma asserção veio depois do passo ou porque o passo não causou
nenhuma mudança visível na UI.

## Quando uma gravação é salva

Sempre termine um teste com uma asserção. No modo `read-write`, o e2e só salva
as gravações de `agent.act` no fim de um teste se uma verificação posterior
passou. Uma verificação no fim confirma todo `agent.act` anterior a ela.

```ts title="tests/cart.e2e.ts"
import { expect, test } from 'e2e';

test('adds an item', async ({ app, agent, screen }) => {
  await app.open('/cart');

  await agent.act('add one item to the cart');

  await expect(screen.getByRole('status')).toHaveText('1 item');
});
```

| Conta como verificação | Não conta |
| --- | --- |
| `expect(locator).toHaveText(...)` e outros matchers de localizador | `expect(value).toBe(...)` sobre um valor simples |
| `expect(browser).toHaveURL(...)` e outras asserções da engine | `expect.poll(...)` |
| `locator.waitFor()`, `browser.waitForURL()` | `locator.textContent()` e outras leituras |
| `agent.assert(...)`, `agent.waitFor(...)` | `agent.extract(...)`, outro `act` ou simplesmente passar |

No relatório JSON, `step.cache.write` registra o que aconteceu com a entrada:

| `step.cache.write` | Significado |
| --- | --- |
| `saved` | Gravada para as próximas execuções. |
| `kept` | Entrada existente mantida como está. |
| `unconfirmed` | Não salva porque nenhuma verificação passou depois do passo. |
| `evicted` | Apagada porque o replay falhou, precisou de reparo ou não foi confirmado antes de uma falha. |
| `no-change` | Não salva porque nenhum controle visível nem a rota mudaram (incluindo passos que só mexem em um [iframe de origem cruzada](/browser#reach-into-an-iframe)). Um passo assim roda ao vivo em toda execução. |
| `not-written` | Não salva porque o armazenamento do cache rejeitou a entrada (por exemplo, por passar do limite de tamanho). |

Se um teste falha no meio do caminho, o e2e ainda salva os passos anteriores
que já estavam confirmados e remove o replay quebrado. Para preservar os
passos de preparação enquanto você depura uma asserção que falha, coloque um
`locator.waitFor()` rápido depois da preparação. Cancelar uma execução deixa
o cache intacto.

<Accordion title="Falhas em que o modelo não conseguiu responder">
Se um teste falha só porque não foi possível alcançar o modelo (nenhum modelo
configurado, chave de API rejeitada, limite de taxa ou indisponibilidade do
provedor), o e2e não remove as suas gravações. Essas falhas não dizem nada
sobre o seu app, então uma execução `read-write` sem acesso a modelo não apaga
entradas do cache que funcionam.

Falhas do fluxo continuam removendo entradas normalmente: saída inválida do
modelo (`MODEL_OUTPUT_INVALID`), estouro de contexto (`CONTEXT_OVERFLOW`),
recusas (`MODEL_REFUSED`), `STEP_TIMEOUT` ou qualquer outra falha na mesma
tentativa (como uma asserção em `afterEach`).
</Accordion>

## O que precisa corresponder

Cada entrada do cache pertence a um teste, um alvo, uma instrução, um
conjunto de parâmetros e um agente. Um cache miss acontece se você:

- renomear o teste, o bloco `describe` dele ou o alvo, ou mover o arquivo de
  teste,
- mudar o texto da instrução ou um parâmetro comum,
- trocar para outro agente ou mudar o `context` / `agentContext` dele,
- trocar de engine, ou mudar `projectId` ou `app.identity`.

Trocar de modelo ou atualizar a engine **não** invalida o seu cache.
Use `--no-cache` quando quiser testar como um modelo novo se sai.

Valores dinâmicos, como timestamps ou e-mails gerados, dariam cache miss em
toda execução. Envolva-os em `unique()` para que o e2e coloque o valor novo no
lugar durante o replay:

```ts
import { unique } from 'e2e';

const name = `E2E ${Date.now()} Company`;
await agent.act('create a company named {name}', { params: { name: unique(name) } });
await expect(screen.getByRole('heading', { name })).toBeVisible();
```

Use `unique()` para dados que o fluxo insere ou exibe, e parâmetros comuns
para valores que mudam o ramo do fluxo (como o nome de um plano). Não
reutilize um valor `unique()` dentro do valor de outro parâmetro, senão o e2e
pula a gravação desse passo.

Para URLs de preview que mudam a cada deploy, defina
[`app.identity`](/reference/config#the-app-under-test) para que as gravações
continuem válidas entre previews. Em dispositivos mobile, o replay identifica
as telas pelo [título da tela](/reference/mobile#replay-cache-on-a-device).

## Rode um teste de novo enquanto o corrige

Mantenha o cache no modo `read-write` (o padrão local) enquanto você itera em
um teste que falha. Os objetivos de preparação anteriores que já foram
confirmados são reproduzidos sem chamadas ao modelo:

1. Rode só o teste que você está corrigindo, pelo número da linha:
   `npx e2e run tests/cart.e2e.ts:3`.
2. Não renomeie o teste nem reescreva objetivos que passam, já que isso
   [causa um cache miss](#what-must-match).
3. Passe `--retries 0` se as novas tentativas estiverem ligadas (novas
   tentativas pulam o replay e rodam todos os objetivos ao vivo).
4. Quando o teste passar, rode-o uma vez com `--no-cache` para confirmar que o
   agente ao vivo ainda alcança o objetivo sem uma gravação.

## Como um replay funciona

1. **Verificar a tela inicial** para garantir que o app está na mesma rota.
2. **Reproduzir cada ação gravada**, identificando os controles por papel,
   nome, test ID e contexto ao redor. O e2e espera os controles aparecerem e
   interrompe o replay se uma correspondência for ambígua.
3. **Verificar o estado final** (a rota final e os controles que apareceram,
   sumiram ou mudaram de estado).
4. **Terminar sem nenhuma chamada ao modelo**, ou passar para o agente ao vivo
   com um resumo do que já rodou.

Texto digitado é reproduzido sem alterações; o preenchimento de um segredo
resolve o segredo atual pelo nome e passa pela autorização de novo.

O replay termina assim que as mudanças de UI gravadas aparecem, o que pode
acontecer antes de o conteúdo mais abaixo na página terminar de carregar. Se o
próximo passo verifica conteúdo assíncrono, use `agent.waitFor` em vez de
`agent.assert`.

<Accordion title="O que conta como a mesma rota">
Uma rota inclui a origem, o caminho e os parâmetros de consulta, ignorando IDs
dinâmicos, tokens, timestamps e fragmentos. Por exemplo,
`/orders/42?t=1727780000` e `/orders/7?t=1727780999` correspondem à mesma
rota, enquanto `?tab=notes` e `?tab=billing`, ou `/products/a` e
`/products/b`, são tratadas como rotas diferentes.

Páginas na própria origem do seu app são comparadas só pelo caminho, então as
gravações funcionam entre URLs de preview que compartilham um `app.identity`.
</Accordion>

<Accordion title="Como a verificação final confere a tela">
- Pelo menos uma mudança gravada precisa acontecer durante o replay (ou a
  última ação precisa navegar para outra rota). Um estado que já estava na
  tela antes do passo não conta.
- Um alerta inesperado que não apareceu durante a gravação interrompe o
  replay.
- Valores voláteis, como datas, durações ou UUIDs gerados, são tolerados desde
  que também tenha acontecido uma mudança estável na UI. Uma contagem com
  rótulo que apareceu na mesma tela (como `3 records imported`) ainda precisa
  corresponder no replay.
- Controles sem nome são identificados pela posição dentro da linha, do item
  de lista ou do grupo com nome que os contém. Se um test ID muda, o e2e passa
  a usar o papel e o nome quando essa correspondência não é ambígua.
</Accordion>

## Por que um passo não foi reproduzido

Cada passo `act` traz os detalhes do cache na
[página de trace](/debugging#traces) e em `result.cache`.

| Resumo da execução | `step.cache.mode` | Significado |
| --- | --- | --- |
| `replayed` | `self-finalized` | Reproduzido por completo sem chamada ao modelo. |
| `handed off` | `agent-concluded` | O replay começou e depois o agente assumiu. |
| `missed` | `missed` | Rodou ao vivo desde o início. |

Quando um passo dá cache miss ou é passado para o agente, o trace mostra o
motivo e em qual ação o replay foi interrompido. Uma gravação `truncated`
nunca é reproduzida, então o reporter padrão também avisa isso na linha do
passo, em toda execução, até o passo mudar:

```text
   ✓ adds a note > agent.act "Add a note to the first row" 9.41s · 3 model calls · not replayed: truncated
```

| Motivo | O que aconteceu | O que fazer |
| --- | --- | --- |
| `no-entry` | Nenhuma gravação corresponde a este passo e aos parâmetros dele. | A próxima execução verificada que passar vai gravá-lo. |
| `retry` | Novas tentativas rodam ao vivo (a menos que `--strict-cache` esteja ligado). | Nada. |
| `invalid-entry` | A gravação está ilegível, é grande demais ou é de um schema incompatível. | Rode `npx e2e cache clear`. |
| `truncated` | A gravação atingiu um limite de tamanho ou de ações ([veja abaixo](#limits-and-gaps)). | Divida o passo em objetivos menores, ou passe os segredos como referências `Secret`. |
| `wrong-context` | O app começou em uma rota diferente da gravada. | Abra a mesma tela antes do passo. |
| `target-not-found` | Um controle gravado não apareceu em 15 segundos. | Se a UI mudou, a próxima execução que passar atualiza o cache. Dê rótulos aos controles sem nome ou coloque-os em contêineres com nome. |
| `target-ambiguous` | Vários controles corresponderam onde a gravação esperava um (ou o número de controles correspondentes mudou). | Dê nomes distintos aos controles repetidos ou use dados de teste únicos. |
| `gap` | Uma ação não pode ser reproduzida com segurança ([veja abaixo](#limits-and-gaps)). | Deixe o agente cuidar dela ao vivo, ou passe valores estáveis por `params`. |
| `action-failed` | O app rejeitou uma ação reproduzida. | Verifique o app. |
| `action-uncertain` | Uma ação reproduzida falhou e pode ter tido efeito; o agente verifica a tela antes de agir. | Verifique o app. |
| `viewport-changed` | Um toque, hover ou arraste por coordenadas foi gravado com um viewport de outro tamanho. | Mantenha o tamanho do viewport constante. |
| `end-mismatch` | Todas as ações rodaram, mas as mudanças de UI esperadas não corresponderam. | Procure dados que sobraram, banners instáveis ou uma regressão real. |

Para descartar o cache como causa ao depurar uma falha, rode uma vez com `--no-cache`:

<CodeGroup>
```bash npm
npx e2e run --no-cache
```

```bash pnpm
pnpm exec e2e run --no-cache
```

```bash bun
bunx e2e run --no-cache
```
</CodeGroup>

### Limites e lacunas

Uma gravação é marcada como `truncated` se um passo executou mais de 50 ações,
digitou uma string com mais de 4.096 caracteres (ou um segredo registrado
diretamente) ou interagiu com um controle sem uma descrição utilizável.

Algumas ações não podem ser reproduzidas com segurança e são marcadas como
`gap`, então o agente ao vivo cuida delas no lugar do replay:

- chamar uma [ferramenta do projeto](/tools) que altera estado,
- digitar um valor que o agente leu da tela (como um código de uso único ou
  token recém-gerado), deduziu a partir da data atual ou leu de uma captura de
  tela.

Valores passados na instrução ou em `params` (assim como valores que o próprio
agente compôs) são reproduzidos normalmente. Em um campo de código de uso
único, ou no campo em foco em um passo que mostrou um campo assim, só é
reproduzido um valor inteiro de dois ou mais caracteres que aparece
literalmente na instrução ou em `params`; códigos digitados em caixas
de dígitos separadas são uma lacuna a partir do primeiro caractere.

## O que uma gravação contém

Cada entrada é um arquivo JSON em `.e2e/cache/` com as ações gravadas, as
descrições dos controles-alvo, o texto digitado, um resumo curto e as
verificações do estado final esperado. As gravações nunca armazenam prompts,
transcrições, capturas de tela, árvores DOM nem valores de segredos (o
preenchimento de um segredo armazena só o nome do segredo).

<Warning>
Valores digitados que não são segredos são armazenados exatamente como foram
digitados. Revise os diffs do cache antes de fazer commit deles ou de
compartilhá-los. Veja [confiança no cache](/reference/security#cache-trust).
</Warning>

## Modos

| Modo | Reproduz | Grava | Padrão |
| --- | --- | --- | --- |
| `'read-write'` | sim | sim | localmente |
| `'read-only'` | sim | não | na CI quando `cache` não está definido |
| `'off'` | não | não | `--no-cache` para uma execução |

```ts title="e2e.config.ts fragment"
cache: 'off',
// or
cache: { mode: 'read-write', dir: '.e2e/cache' },
```

`--no-cache` prevalece sobre a configuração para uma execução. No modo `read-only`,
entradas desatualizadas ficam intactas até que uma execução `read-write` as
substitua. Um `cache.store` personalizado substitui o armazenamento em
arquivos e não usa `read-only` por padrão na CI. As sessões interativas de
`e2e explore` e de `e2e mcp` não usam o cache (exceto quando o MCP roda um
teste via [`open_session {test}`](/reference/mcp#running-a-test)).

## Compartilhe o cache entre checkouts

Aponte vários checkouts ou worktrees para uma única pasta compartilhada com
`E2E_CACHE_DIR` ou `--cache-dir`. Dê a cada checkout o mesmo `projectId`
(ou, no `package.json`, o `name`) para que as entradas correspondam entre
caminhos diferentes.

- As escritas são atômicas, então execuções em paralelo podem compartilhar o
  diretório. Os checkouts compartilham entradas, então uma execução que falha
  em qualquer checkout remove a entrada compartilhada, e branches diferentes
  com a mesma identidade de app sobrescrevem as entradas umas das outras.
- Enquanto a substituição estiver definida, um cache commitado em `cache.dir`
  não é lido.
- Mantenha um diretório por projeto para que o `--strict-cache` não confunda
  entradas de outro repositório.

```bash
E2E_CACHE_DIR=~/.cache/my-app/e2e npx e2e run
```

## Faça commit do cache de replay

<span id="commit-your-traces" />

`e2e init` adiciona `.e2e/cache/` ao `.gitignore`. Para compartilhar as
gravações com o seu time e com a CI, remova essa linha e faça commit de
`.e2e/cache/`. A CI usa `read-only` por padrão, então ela reproduz as entradas
commitadas sem modificá-las.

Execuções locais mantêm o seu diff do git limpo: o e2e só reescreve um arquivo
do cache quando um passo é gravado pela primeira vez, se autocorrige depois de
uma mudança na UI ou é removido, ou quando uma atualização do `e2e` muda o
formato da chave do cache.

## Falhe quando uma gravação estiver desatualizada

Por padrão, se uma gravação commitada deixa de corresponder ao app, o agente
ao vivo assume, e a CI paga por chamadas ao modelo em toda execução até que
alguém atualize o cache. Passe `--strict-cache` (ou defina
`cache: { strict: true }`) para falhar na hora em vez de chamar um modelo:

<CodeGroup>
```bash npm
CI=1 npx e2e run --strict-cache
```

```bash pnpm
CI=1 pnpm exec e2e run --strict-cache
```

```bash bun
CI=1 bunx e2e run --strict-cache
```
</CodeGroup>

O modo estrito faz falhar com `REPLAY_STALE` (código de saída 2, sem nova
tentativa) toda gravação cuja UI ou chave do cache mudou, e nunca escreve nem
apaga arquivos do cache. A detecção de chave alternativa só vale para o
armazenamento em arquivos embutido (não para um `cache.store` personalizado),
e passos que ainda não foram gravados, que esbarram em uma falha de leitura do
armazenamento ou que têm uma gravação `gap` ou `truncated` ainda rodam ao
vivo.

Para atualizar uma gravação desatualizada:

1. Rode o teste localmente no modo `read-write` sem `--strict-cache` (desligue
   `cache.strict` se a sua configuração definir essa chave).
2. Faça commit do arquivo do cache atualizado.

## Inspecione o cache

<CodeGroup>
```bash npm
npx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
npx e2e cache stats   # entry count and size
npx e2e cache clear   # delete every entry
```

```bash pnpm
pnpm exec e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
pnpm exec e2e cache stats   # entry count and size
pnpm exec e2e cache clear   # delete every entry
```

```bash bun
bunx e2e cache ls      # one row per entry: test, target, instruction digest, age, actions
bunx e2e cache stats   # entry count and size
bunx e2e cache clear   # delete every entry
```
</CodeGroup>

<Note>
A porcentagem `cached` no uso de IA é o cache de prompt do provedor. Ela reduz
o custo de uma chamada ao modelo. O cache de replay evita a chamada.
</Note>
