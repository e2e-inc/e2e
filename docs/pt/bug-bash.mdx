Um bug bash roda muitas sessões de `e2e explore` ao mesmo tempo, cada uma em
uma área do app. Depois, um agente de código escreve um teste para cada achado
e só o relata como bug quando o teste falha.

<Video>
  <video src="/images/bug-bash.mp4" aria-label="Um agente de código roda um bug bash em navegadores com interface visível." muted loop playsInline controls />

  Cada navegador é uma sessão de explore.
</Video>

## Antes de começar

- Garanta que o seu app consiga atender vários exploradores ao mesmo tempo.
  Ou inicie o app uma vez com `reuseExisting: true` no `app.command`, ou use
  a porta `0` na URL para que cada execução tenha a própria cópia. (Na CI, o
  e2e ignora `reuseExisting`, então use a porta `0`.) Veja
  [Iniciar seu app](/web#starting-your-app).
- No mobile, configure um alvo por simulador ou emulador, para que cada
  explorador tenha o próprio dispositivo.
- Cada sessão de explore faz chamadas ao modelo e, ao terminar, mostra o uso
  de tokens, o custo e a duração.
- Não altere dados em um site compartilhado ou de produção.

O agente faz o resto da configuração, como as contas pré-carregadas e o
login, a partir da skill.

## Instale a skill

O agente de código roda o bug bash a partir da [skill `e2e`](/coding-agents),
que o `e2e init` instala. Para instalá-la sem o `init`:

<CodeGroup>
```bash npm
npx skills add e2e-inc/e2e
```

```bash pnpm
pnpm dlx skills add e2e-inc/e2e
```

```bash bun
bunx skills add e2e-inc/e2e
```
</CodeGroup>

## Inicie um bug bash

Dê um prompt ao seu agente de código:

```text
Bug bash the checkout and account settings on this branch.
```

## O que o agente faz

<ShowMore id="bug-bash-steps">

1. Lê as rotas do app. Em uma branch, também lê o diff.
2. Escreve de 5 a 10 charters. Um charter é um objetivo de uma frase para uma
   área, com uma postura: usuário novo, números e textos, entrada de caso de
   borda, estado depois de recarregar ou caminhos de erro.
3. Roda um `e2e explore` para cada charter, 4 ao mesmo tempo, cada um com sua
   própria persona (`--agent`) e seu próprio diretório de saída (`--output`).
4. Junta os achados de todos os charters.
5. Rejeita os achados que têm uma causa conhecida. A causa pode ser um limite
   do explorador (por exemplo, um link que abre uma nova aba), o ambiente
   local, o design pretendido ou os dados pré-carregados.
6. Escreve um teste de reprodução para cada achado restante: os passos do
   achado como chamadas `agent.act` e o comportamento esperado dele como o
   `agent.assert` final. Ele pode iniciar um subagente por área.
7. Roda os testes de reprodução. Um achado só é confirmado como bug se o
   teste de reprodução dele de fato falhar no defeito relatado.
8. Relata, nesta ordem: bugs confirmados, riscos de produção que ele não
   consegue verificar localmente, achados rejeitados por motivo e avisos.

</ShowMore>

Cada bug confirmado tem o próprio teste de reprodução e os passos. Ele também
tem a captura de tela e o vídeo do explorador quando a engine os grava.

<Warning>
O vídeo não é mascarado. Se o explorador digitou uma senha, confira o vídeo
antes de compartilhá-lo.
</Warning>

Para ler o procedimento completo, rode `npx e2e guide bug-bash`.

## Testes de reprodução

Um teste de reprodução falha até que o bug seja corrigido. O agente marca
cada um com a tag `bugbash`. Deixe-os fora da execução que bloqueia merges:

<CodeGroup>
```bash npm
npx e2e run --exclude-tag bugbash
```

```bash pnpm
pnpm exec e2e run --exclude-tag bugbash
```

```bash bun
bunx e2e run --exclude-tag bugbash
```
</CodeGroup>

Depois da correção, o teste passa. Remova a tag e mantenha o teste como um
teste de regressão.
